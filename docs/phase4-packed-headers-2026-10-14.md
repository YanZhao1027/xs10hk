# 第四阶段：X6 固件压缩段头定位（2026-10-14）

## 摘要

对用户依法取得、仅在 Ubuntu 电脑上分析的两份官方固件：

- X-S10 3.11：原始 `FWUP0025.DAT` SHA-256 `141e8c3882dd456d3b954fd1dd3681b86e7d001f617dca2fb8d8dfd4f7eede53`
- X-T4 2.12：原始 `FWUP0024.DAT` SHA-256 `853d273b5603d3a2b93493f0ebd6a762b0b4b6bdc70317777775ae5f8ed93bc5`

定位到**两机各四个非常可信的压缩段头候选记录**，并从字节字段读出压缩前/后大小。计算的压缩率与 [fffw 开发分支公开测试数据](https://github.com/tiredboffin/fffw/blob/develop/ffun/lz-all.tsv) 中同型号版本的四个比值吻合。

> 这已经超越了字符串搜索，但仍不是解压成功、也不是主程序运行时内存映射成功。没有找出 X-S10 可用的 HEVC 初始化调用链，更没有可安全刷写的补丁。

## 已观察到的共同头部模式

以**去除 DAT 外层并按 FujiHack 规则逐字节取反后的本地 payload** 为基准：

- 候选头位于 `0x20000` 对齐分区起点之后 `+0x60` 字节。
- 头部前两个小端 `uint32` 分别与 **解压后字节数**、**压缩后字节数**高度吻合。
- 后续结构在所有八处观察值中，`header + 0x0c` 的 `uint32` 均为 `0x4000`，`header + 0x10` 的 `uint32` 均为 `4`。
- `header + 0x08` 的整数值因段而异，目前只记录，暂不赋予具体含义。
- 尚未查明压缩流真正开始的字节位置、解压算法、校验值及装载地址，**不能拿这几个数直接做解压或运行时补丁**。

这些共同约束可以在不使用相机的条件下，通过 `tools/packed_headers.py` 自动发现。

## 静态区域对齐的额外结果

使用 `tools/align_images.py` 扫描两份文件，排除纯 `FF`/全零等低信息量块并限制为各文件唯一的 4 KiB 哈希锚点，观察到以下对齐：

- X-T4 `0x01860000` ↔ X-S10 `0x01660000`：连续 **1,536,000 字节相同**，二者之间文件偏移差 `-0x200000`。
- X-T4 `0x027BE000` ↔ X-S10 `0x027DE000`：连续 **1,024,000 字节相同**，文件偏移差 `+0x20000`。
- 视频编解码器候选区域：不同模块位置的偏移差为 `+0x160000`，此前已逐字节比对一致，见 [第三阶段报告](phase3-xt4-compare-2026-10-14.md)。

这些是**文件位置关系**。尤其是第一项 1.536 MB 公共区域目前无法判定类型，不得未经查证将其归为 IBIS/视频模块。多种位移关系也证明不能对整个 X-T4 文件简单加一个常数后当作 X-S10 的地址空间。

## 第三方研究与技术限制

- [tiredboffin / fffw](https://github.com/tiredboffin/fffw) 将 X-S10 和 X-T4 归于 **FF4230 / X6** 家族，其开发分支 [lz-all.tsv](https://github.com/tiredboffin/fffw/blob/develop/ffun/lz-all.tsv) 记录 X-S10 0311 的压缩率约 `2.05/1.78/2.20/1.94`，X-T4 0212 约 `2.15/1.80/2.21/1.95`。这与独立从两份文件头读出的比值相匹配。
- 该研究者指出固件使用并非直接兼容通用解压工具的 LZ 家族变体，其 `ffun` 完整解包/地址映射工具目前未完整公开：[ffun README](https://github.com/tiredboffin/fffw/blob/main/ffun/README.md)。
- 对 Ghidra 的 `ARM:LE:32:v7` 扁平导入不能代替解压和重定位。只有重建装载地址、识别真实可执行段并验证交叉引用，才能说“找到 HEVC 初始化代码”。

```bash
cd /home/zyubuntu/xs10hk
```

截至此报告，**20 项单元测试通过**。所有计算处理原厂固件的只读本地副本；脚本不向相机发任何 USB 指令，不生成刷机文件，公开仓库也不提供原厂或解包后的固件。

## 之后最有价值的研究方向

1. 从公共文件头、启动代码以及同系列资料中验证压缩流的实际起点和结束位置，重建 LZ 变体的**只读解码器**，并用检查长度、端点及映像里的字符串验证输出。
2. 解压并重建文件偏移到真实 RAM 地址的映射；对每个解出的主程序分段单独导入 Ghidra，确认 ARM32 / Thumb 指令边界。
3. 从 X-T4 已知 HEVC / Main10 视频配置与 `V61` 驱动参考出发找真实调用者；比较 X-S10 相应代码与数据表，在确认能够触达硬件前不推断其功能。
4. **暂不接入隐含服务模式、不拆机、不刷写自定义固件**；实际可能涉及可靠恢复方式和许可限制，需独立确认。
