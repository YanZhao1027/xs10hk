# 第69阶段：原厂接口模式默认优先级包含多条数值60记录，但并未默认枚举97/102（2026-10-27）

## 1. 核心证据：默认候选与原始36记录表之间真正的索引关系

**X-S10研究固件 3.11 / X-T4研究固件 2.12 的原厂Section1，不仅拥有第68阶段独立核验的36条×16字节接口描述符表，而且在这张表前14字节存放了完全相同的默认** `0xFF` **结束的优先级索引序列。**此序列会在原厂初始化函数中复制到独立的运行态RAM数组，并非只是 ROM 里无人引用的字节。

| 证据 | X-S10 3.11 | X-T4 2.12 |
|---|---|---|
| 36条接口描述符表的原始地址 | `0x0162DE0A` | `0x01605D2E` |
| 默认优先级表地址 | **`0x0162DDFC`** | **`0x01605D20`** |
| 原厂默认优先级索引 | `11,10,9,8,7,5,4,0,FF` | 完全相同 |
| 初始RAM优先级复制调用者 | `FUN_0126BF9C` | `FUN_012421B4` |
| 默认表作为实际参数传入复制器 | `FUN_0126989C(&DAT_0162DDFC,0)` | `FUN_0123FAB4(&DAT_01605D20,0)` |
| 真实A32 `BL` 地址 | `0x0126BFCC` | `0x012421E4` |
| 运行时优先级更新包装器 | `FUN_01269960` | `FUN_0123FB78` |
| 该包装器实际A32 `BL` | `0x01269978` | `0x0123FB90` |
| 运行时优先级复制器 | `FUN_0126989C` | `FUN_0123FAB4` |
| 候选选择器 | `FUN_0126B508` | `FUN_01241720` |
| 候选逐条分类器 | `FUN_012696E0` | `FUN_0123F8F8` |
| 运行时ID支持列表校验器 | `FUN_01269634` | `FUN_0123F84C` |

默认索引直接查的是上述**接口描述符**，而不是第46阶段96×64 B的录像分辨率/帧率ROM模式矩阵。两机的默认顺序按值展开：

| 默认索引 | 接口ID（描述符+0） | 描述符+0x0A数值 |
|---:|---:|---:|
| 11 | 16 | **60** |
| 10 | 31 | 50 |
| 9 | 34 | 30 |
| 8 | 33 | 25 |
| 7 | 32 | 24 |
| 5 | 5 | **60** |
| 4 | 20 | 50 |
| 0 | 3 | **60** |

**必须纠正两个相反的误解：**默认优先级**没有**索引22/23(ID97)/34/35(ID102)，但**包含**索引11/5/0这三条数值60记录（ID16/5/3）。因此既不能说“默认完全没有60”，也不能说“ID97/102是默认就选的4K60”。

## 2. 同一张接口表中确实有不同类别的数值60

原厂36条接口描述符的十六字节结构里，`+0x00`存接口模式ID，`+0x01`子代码，`+0x02`条件/门控字节，`+0x0A`为取值24/25/30/50/60的数值。两机原始全部576字节逐字相同，本阶段**只公开少量字段的业务核对结果，不公开原始ROM字节**。

- 描述符数值60的全部索引：**`0,3,5,11,22,23,34,35`**。
- 默认优先级包含的数值60：索引**11/5/0**，对应ID **16/5/3**，且原厂`+0x02`条件字节为0。
- 非默认优先级的数值60：索引**22/23/34/35**，对应ID **97/97/102/102**，且原厂`+0x02`条件字节为1。分类器在条件为1的行上会根据另一运行态字节决定是否检查当前主支持ID列表，所以不能直接把这两组记录视为同一场景或一模一样的逻辑。
- 另有索引3(id4)也是数值60，但同样**不在默认顺序**。总计8条数值60，不是6条或仅4条。

所谓数值60仅是**原厂接口描述符+0x0A中的数值字段**；没有独立的物理传感器模式定义、时钟/行读出证据、真实ISP输出或与2160P模式表之间的调用关联，不得直接将它写成实体X-S10的4K60传感器读出能力。即使该字节最终是帧率数值，也不能从数值60推导输出分辨率、色深和持续带宽。

## 3. 默认复制之外，原厂确有运行时候选重排与支持ID名单

默认数组初始化以后，另一条独立的原厂代码会将**RAM指针**指向的`0xFF`结尾索引列表再次复制到相同优先级数组：X-S10 `FUN_01269960` 使用 `_DAT_01C84F58`，X-T4 `FUN_0123FB78` 使用 `_DAT_01BE5024`，另外两机各有两处相同动态指针的更新调用。真实A32 `BL` 及只读Ghidra拷贝函数同时确认它们**更新的是序列值，不是把整份原厂36行表复制给另一个参数**。

真正的选择器在优先级列表中遍历**索引0–35**（`<0x24`边界），将索引传入读取描述符的分类器；分类器会查询运行时支持ID名单（还有第二条件名单、描述符标志和状态字节）。该ID名单通过一条解析标记为 **`0x302`** 的运行时数据包路径更新，其中有数据段类别2、长度边界`0xC0`、字节值处理；并非只靠ROM固定默认值。选择器还接受另外的运行态模式输入 `0x3840/0x3841`，在某些分支跳过默认优先级；特殊状态可导致候选回退或另外的结果标记。**真实数据包、候选顺序、是否出现ID97/102与最终外设响应均未观察到。**

因此“X-S10默认没有索引22/23/34/35”并不等于“这四条永远不会被使用”，也不证明“只要手动指定这些索引就能录4K60”。本阶段未向设备写任何索引或消息；所有结论仅关于静态原始固件代码。

## 4. 与Phase68四参数联合模式表的关系与研究边界

第68阶段（[Draft PR #47](https://github.com/YanZhao1027/xs10hk/pull/47)）已将`eaPixel_Movie`、`eAspect`、`eMovieFps`与`eMovieBps`四项原厂ROM菜单允许表和设置加载器的回退/覆写分支结合；第67阶段同时证明类别0、像素键7、画幅2或7、普通FPS6、BPS1/2/3对应六条静态2160P条目。但此处的**接口描述符索引0–35**与**Movie模式矩阵行号0–95**是不同的两个索引空间，当前没有证据显示索引22/23/34/35会导致Movie查表的2160P行15–17或33–35被选中。

真正的下一步必须找到：哪一次Movie录像初始化调用携带哪个接口候选索引，哪条运行时消息真正返回了这个ID的支持结果、以及sensor/ISP输出尺寸和VPU的成功反馈。不连实体相机，只能继续尝试更强的只读 ROM 静态条件和业务标识交叉验证；**既不能宣布软件已经4K60，也不能断言硬件绝对不支持**。

## 5. 离线复验与非侵入性

- `tools/audit_stage69_interface_default_priority_runtime_override.py`首先重跑第68阶段及全部此前SHA固定原厂ROM审计，然后只读取Section1原厂默认优先级前缀和576字节描述符（仅本机），校验索引0/3/5/11/22/23/34/35、ID16/5/3/97/102及独立门控字段；继续用原始A32 BL+Ghidra只读代码核对默认数组真正导入、运行时RAM指针重拷、候选迭代与标记`0x302`的ID名单解析。
- `tests/test_audit_stage69_interface_default_priority_runtime_override.py`纯合成记录/伪Ghidra输入，包含边界、负例与错误成员ID/数值60/BL/动态复制器突变；**不使用厂商ROM字节或完整日志文本**。
- X-S10研究样本为**3.11**、X-T4为**2.12**，历史实体X-S10报告**2.10**，相应内存地址不能移植。无USB/FF80、机身RAM或Flash访问、ROM/DAT修改、补丁和刷写；私有原厂Section1/2、Ghidra数据库及日志继续Git忽略存放于用户Ubuntu `output/`，GitHub只分享原创审计、合成测试和报告。

**结论：默认60数值候选与附加60数值候选在静态ROM和运行时分类门控上都可区分，但不存在实机4K60/Main10输出成功证据。**
