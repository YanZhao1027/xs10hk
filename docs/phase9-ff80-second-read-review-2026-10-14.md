# 第九阶段：第二次 FF80 RAM 读取的离线可行性审核（2026-10-14）

> 结论：**暂不对恢复正常开机的 X-S10 再执行任何 FF80 RAM 读取。**
> 此决定不是因为用户没有授权；用户明确希望继续尝试。暂停的原因是上次现场实验造成维修接口失去响应、相机拨 OFF 后仍红灯常亮、必须移除电池才能恢复；离线审查目前未找到能实质降低再次卡死风险的已验证新方法。
>
> **本阶段全部操作只在 Ubuntu 本地固件文件及 GitHub 源码上进行，没有再次连接或操作相机的维修接口。**

## 本次离线核对：协议封包是否有明显错误？

根据 [fffw/ff80/ffjlib.py](https://github.com/tiredboffin/fffw/blob/main/ff80/ffjlib.py) 及 [fffw/ff80/fftlib.py](https://github.com/tiredboffin/fffw/blob/main/ff80/fftlib.py)，单次 16 字节 RAM 读取应当采用以下字段：

| 字段 | 上次实验所用 | 上游参考实现 |
| --- | --- | --- |
| 诊断操作码 | \`0x00200001\` | \`0x00200001\` |
| 子操作 | \`2\`（debug_read_ram） | \`2\` |
| 参数块（4 × uint32 little endian） | \`(0, 0, 0x0, 16)\` | 同一布局 |
| 命令数据长度 | 36 字节（20 字节操作头 + 16 字节参数） | 36 字节 |
| USB 读取回复期望长度 | 52 字节（36 + 16） | 52 字节 |
| 访问前调试配置 | \`0xF7=1\`，已读回 | 作者的 \`ram read\` 也会先尝试开启调试 |

通过 \`tests/test_ff80_protocol_vectors.py\` 新增的 4 项**完全离线合成协议测试**核对实际类的输出报文与独立转写的上游格式。结果 **4/4 通过**，项目合计 **43 项测试通过**。

这**只证明报文布局与现有上游代码一致**，不证明上游代码本身适配 X-S10，也不能排除 USB 时序、异常处理、设备状态和固件差异等问题。运行时芯片/USB 栈可能在处理请求时挂起，正如上次已经发生。

## 两个更关键的未知问题

### 1. 地址 \`0x0\` 不是 X-S10 专属验证过的内存范围

作者的 [Route 0xff80 研究笔记](https://github-wiki-see.page/m/tiredboffin/fffw/wiki/Route-0xff80) 使用 \`0x0\` 作为**跨机型**示例，并指出 X-Processor Pro 及后续机型采用 MMU，使某些内存区域受保护。笔记中关于“可以读取普通内存”的经验不等于证明所有型号的 \`0x00000000\` 一定映射 RAM。

我们的 X-S10 在 \`0xF7=0\` 时读取地址 0 的 16 字节，返回 \`0x1/0xFFFF\` 错误；随后临时设置 \`0xF7=1\` 且读回确认，重复读取相同地址时 USB 固件接口没有返回，最终需要取出电池恢复启动。

这不能确定真正原因。**换个随机或从其它机型推测的地址，不构成更安全的实验。** 还需要 X-S10 2.10 的有效 RAM 虚拟地址表、映射保护属性和 FF80 读取函数适配证据。

### 2. 现场运行版本与已分析固件版本不同

实际 USB 标准 PTP 曾两次确认 X-S10 运行 \`2.10\`，而 Ubuntu 本地提取并与 X-T4 比较的是 X-S10 固件 \`3.11\`。FF80 标签 \`1.60\` 的含义不明。即使能从离线 \`3.11\` 推导运行时地址，也不能直接套用到实际 \`2.10\`。

当前公开 FujiHack \`fujihack/model/\` 已有 X-T4 等一些机型数据，但没有可直接复用的 X-S10 RAM 配置；[fffw/ffun](https://github.com/tiredboffin/fffw/blob/main/ffun/README.md) 声明完整 DAT → 运行时 ELF / 内存地址清单实现尚未公开。公开仓库里 \`ffcompress\` 引用了未发表的 \`fflz\` 包，**不能直接依赖它做 X-S10 完整解压和地址确认**。

## 为什么“最终计划刷机”不能直接推出“现在必须读取 RAM”

修改固件最终可能需要写入，但 RAM dump 是研究途径之一，不是绝对先决条件。

合理的研发顺序是：

1. **静态功能证明**：验证 X-S10 的 HEVC/Main10 是否拥有有效的编码初始化、像素格式配置、驱动调用与存储流水线；共享 HEVC 候选数据并不能直接证明这些调用。
2. **完全离线构建**：掌握 X6 压缩算法、分段/重定位、校验和/签名、机型与固件版本验证，能复现出与原版匹配的固件包，而不是先刷入盲测补丁。
3. **恢复预案**：实证 X-S10 是否存在独立于损坏主固件的恢复入口；搞清官方 SD 更新能力、哪些分区会被覆盖，以及发生失败时应向谁求助。FujiHack 公共资料明确表示其 SoC boot ROM 救砖路径未完成逆向，不能视作已建立的 X-S10 救砖方案。
4. **实机验证**：只有确定新方案与上一次不同、地址范围有效、错误及超时恢复可预期，且用户接受仍可能永久故障的风险，才考虑在可承担损坏成本的机身上重新试读。

## 后续实机试读的必要条件

至少需要满足：

- 有**针对 X-S10 2.10**、可追溯且可交叉验证的 RAM 区间及读保护信息；不能猜 \`0x0\` 或拿 X-T4 地址照搬。
- 有经过**失败场景测试**的 FF80 RAM 读取协议实现；不能把 Python \`finally\` 当作设备卡死后的恢复保证。
- 诊断调试位 \`0xF7\` 的写入、复位和持久化语义有 X-S10 实机或静态证据。
- 不依赖 FF80 接口继续正常响应的异常恢复/退出步骤；清楚主机掉线/相机停机后的损失上限。
- 若目标是后续修改主固件，还需要独立验证的刷机失败恢复策略；优先在备用研究机测试。

在条件未满足前，重复同一地址的读取预计只会重演失败；猜其它地址也无合理依据。
