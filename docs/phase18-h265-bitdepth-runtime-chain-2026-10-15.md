
# 第十八阶段：真正的 H.265 位深字段与 VPU 会话格式分支已经找到（2026-10-15）

> **本阶段核心进展**：从三台机型各自的底层驱动字面错误信息 `#init bit_depth ERROR` 反查至真实执行的 ARM 参数验证，再上溯到录像业务创建的 400 字节驱动初始化结构，并向下贯通至视频会话构建函数的格式分支。**X-T3 5.11、X-T4 2.12、X-S10 3.11 的 H.265 初始化代码全部给独立位深字段 `+0x0C` 写入 `1`，三机使用同一判断，都会在会话格式构建中将非零值分派为 `0x0121`，零值分派为 `0x0201`。**
>
> 这比仅比较通用设置表和 H.265 编码器代码更加深入：已证实 X-S10 不是在这个通用 H.265 驱动初始化位置硬编码为位深枚举 `0`，其数值 `1` 能沿驱动状态进入后续处理。
>
> **严肃限定**：目前仍不能独立断言“富士内部枚举 `1` 的正式定义就是 Main10”。从官方 X-T3、X-T4 支持机内 H.265 10-bit 的事实和三机统一的 H.265 参数值看，`1` 很有研究价值；但是 **没有抓到 X-S10 实际输出的 HEVC SPS NAL、没有确认 `general_profile_idc=2` 与 `bit_depth_luma_minus8=2`、也没有真正启动 X-S10 的 HEVC VPU 会话**。因此既不是 10-bit 内录功能已可用的证明，也不是可刷机补丁。
>
> 所有工作均为**授权 Ubuntu 上离线原厂固件数据、Ghidra 私有分析项目及合成测试**，没有相机 USB/FF80 通信，没有刷写；X-S10 实机曾显示 2.10，离线研究固件是 3.11，地址禁止用于机身实时操作。

## 1. 错误日志反向定位：驱动确实独立检查 bit_depth

直接在 X6 `section-1.bin` 搜索完整诊断文本 `#init bit_depth ERROR`，再用 Ghidra 查询对完整字符串**起点**的引用，每台相机均找到唯一一个 ARM 代码交叉引用。

| 项目 | X-T3 5.11 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- | --- |
| driver init 函数 | **`0x01098ECC`** | **`0x011CCE88`** | **`0x011F97DC`** |
| Ghidra 识别函数长度 | 936 字节 | 936 字节 | 936 字节 |
| `#init bit_depth ERROR` 字符串 | `0x013EFCA8` | `0x0158DB68` | `0x015B62A8` |
| 单一引用指令地址 | `0x010990AC` | `0x011CD068` | `0x011F99BC` |
| 输入字段 | `param_2 + 0x0C` | `param_2 + 0x0C` | `param_2 + 0x0C` |

三机驱动的核心判定完全一致：

~~~c
if (init.video_codec == 0 && init.bit_depth > 1) {
    log("#init bit_depth ERROR");
    return -1;
}
~~~

其中 `video_codec` 在结构偏移 `+0x188`，`bit_depth` 在 `+0x0C`。此判定表明对于 `video_codec=0` 分支，bit_depth 候选 0/1 均不因**这条检查**被拒绝，但**其它驱动或 VPU 检查仍可能存在**；绝不可只凭此句宣称编码硬件支持任何配置。

## 2. 正对照与 X-S10 的 400 字节初始化结构全都写入 bit_depth=1

三个录像任务的实际编码会话初始化入口（已由第十四阶段 Ghidra ARM BL 与业务代码确认）：

| 机型 | 录像业务函数（Section 2） | 初始化结构地址 | `init+0x0C` 的真实赋值 |
| --- | --- | --- | --- |
| X-T3 | `FUN_01F0318C` | `0x0246BF60` | **`_DAT_0246BF6C = 1;`** |
| X-T4 | `FUN_0224B65C` | `0x028A5150` | **`_DAT_028A515C = 1;`** |
| **X-S10** | **`FUN_022DEE64`** | **`0x02945A08`** | **`_DAT_02945A14 = 1;`** |

该初始化结构除了 bit_depth 还含宽高、码流缓存地址、帧缓存、工作缓存、VPU 微码地址、`video_codec` 等。下层 H.265 驱动验证后，**复制整个 400 字节输入**到各自的局部初始化状态。视频驱动事件进入 `V61_drv_init` 会话处理时，读取存下的 bit_depth，并写入 **运行时会话 DWORD `[3]`**。

| 机型 | 驱动 init 状态构建 | 本地复制的 bit_depth 来源 | 写入目标 |
| --- | --- | --- | --- |
| X-T3 | `FUN_01097B48` | `_DAT_018D272C` | 会话结构 `[3]` |
| X-T4 | `FUN_011CBB0C` | `_DAT_01B840E4` | 会话结构 `[3]` |
| X-S10 | `FUN_011F8460` | `_DAT_01C2597C` | 会话结构 `[3]` |

三机另有一条**编码/解码选择字段非零时将运行时 bit_depth 强制赋值 1** 的对应分支；这并不削弱本次结论，因为录像业务层三个固定值本来就是 1，而且我们没有任何理由用这一分支推测录制成功。

## 3. bit_depth 不是死字段：会话格式分支确实使用它

下一个相同逻辑的函数负责生成缓冲/会话描述：

| 机型 | 会话描述生成函数 | bit_depth == 0 | bit_depth != 0 |
| --- | --- | --- | --- |
| X-T3 | `FUN_0109A248` | `0x0201` | `0x0121` |
| X-T4 | `FUN_011CE204` | `0x0201` | `0x0121` |
| X-S10 | `FUN_011FAB58` | `0x0201` | `0x0121` |

三机代码均实际在会话参数 `[3]` 上测试零/非零，并向结构 `+0x18` 写入不同的 16-bit 描述符，0 条件与非零条件分别为 `0x0201` 与 `0x0121`。

**它是一个后续会话处理使用的有效格式选择，不是 UI 假开关。** 但 `0x0121` 的具体 VPU SDK 格式定义仍未验证，暂不命名为“Main10 像素格式”。

## 4. 与第十四阶段可疑的 `input[3]=1/3` 字段严格区分

容易误把这次 `bit_depth=1` 与上次提到的 60 字节 H.265 **编码参数** `input[3]` 混为一谈。本次已经进一步追到它们的不同消费者：

| 源结构 | 偏移 | X-T3 | X-T4 | X-S10 | 下游 |
| --- | --- | --- | --- | --- | --- |
| **400B H.265 驱动初始化** | **`+0x0C`** | **1** | **1** | **1** | 位深合法性验证 → 运行时会话 `[3]` → 缓冲/会话格式描述 `0x0121` |
| **60B H.265 编码参数** | **`+0x0C`** | 1/3 | 1/3 | 3 | 编码状态 → H.265 **`0x0A` 选项包**，包含该值与相邻码率相关参数 |

第二条 H.265 编码参数的驱动继续构造 `0xBBB` 类别、选项 ID `10`（`0x0A`）、有效 payload 长度 `0x0C` 的消息，将先前 `input[3]` 与同一 60 字节编码参数的 `input[4]` 一起送往下一层 VPU 通信接口。

| 机型 | 组建 HEVC 选项包的函数 |
| --- | --- |
| X-T3 | `FUN_0109A6A0` |
| X-T4 | `FUN_011CE65C` |
| X-S10 | `FUN_011FAFB0` |

紧邻 `input[4]` 的源数据来自录像设置计算出的编码速率/数据量相关字段，而不是 bit_depth 原始字段。**这提示 `input[3]` 可能与压缩/码控模式关联，但其厂商协议定义还没有验证**。数值 1 或 3 **不能直接命名为 10-bit/Main10**，更不能凭这个差异直接生成补丁。

三台相机还都在 `FUN_...SndSetOption` 中发送条件相同的 `0x80008`、`0x26` 类别选项，这个字面值也不能作为 X-S10 独有限制或 Main10 唯一指标。

## 5. 与已知可用的正对照结合，究竟证明了什么？

**确实得到的三项结果：**

1. 原厂 X-T3、X-T4 的内录 H.265 10-bit 路径所在驱动源码内，同样的 400B 初始化 `bit_depth` 参数设为 `1`。
2. X-S10 录像任务做出同样赋值，并经过内容一致的 936B 初始验证函数；`bit_depth=1` 不是该函数禁止的取值。
3. 这个数值会进入实际会话选择分支，导致生成同样的内部描述符 `0x0121`。

**尚未完成的三项验证：**

1. **确切 Main10 码流定义**：需要得到 X-T3/X-T4 真实录像的 VPS/SPS 样例以标定正对照，后续若有经过安全恢复机制的 X-S10 HEVC 录制样例，还应检查 SPS 的 `general_profile_idc=2`、`bit_depth_luma_minus8=2` 和 `bit_depth_chroma_minus8=2`（实际 10-bit、4:2:0）。目前没有任何 X-S10 H.265 实机码流。
2. **上层模式选择真正可达**：通用权限矩阵允许 H.265，并不代表 UI/录像任务就必定请求它。4K60 的传感器 ISP/VPU/存储吞吐也需独立确认。
3. **可安全刷写**：DAT 封装重压缩、校验/可能签名、实机 v2.10 的地址相容性和独立救砖机制均未验证；此外先前 FF80 RAM 试验曾使机主需要断电恢复，不能复用危险路线。

此阶段因而**更有力支持 X-S10 保留 Main10 相关驱动能力代码的假说**，但尚未证明整机机内 10-bit 视频功能可解锁。

**下一研究目标：**找出 VPU 对 `0x0121` 和 `0x0A` packet 第 1 DWORD 的真正协议定义，或以原厂 X-T3/X-T4 已知 10-bit 成品片段解析其 SPS 来标定；再比较 XS10 的 UI→codec=1 触发完整条件，进而判断是菜单禁用还是硬件能力限制。**不应从“发现位深枚举相同”直接跳到刷机。**
