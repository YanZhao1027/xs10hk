# 第29阶段：Recorder 模式配置注册表的实际写入来源（2026-10-15）

> **本阶段结论**：找到 X-S10 原厂 3.11 / X-T4 原厂 2.12 的“模式选择 → 配置注册表 → 当前描述符”真实 ARM 复制路径。两机上游代码读取当前配置缓冲区 +0x04 字节，选择配置类型 **0x206**（该字节为零）或 **0x207**（非零），第二参数固定 **0x8C**；接着分别复制 12 字节头部和一段运行时变长载荷到描述符。载荷目标从描述符 +0x0C 开始，若复制长度 >=8 字节，将覆盖整个描述符 +0x10 的四字节主缓冲区指针。**配置载荷长度、动态地址和 Codec 字节的运行时值仍未知；这不是内录 HEVC Main10 或 4K60 解锁。**

安全范围：仅对授权 Ubuntu 中已经解压的 X-S10 3.11、X-T4 2.12 原厂 X6 固件进行只读 Ghidra 12.1.4 / 原始 Section2 检查。用户之前报告的真实 X-S10 固件为 2.10，不能将研究地址直接写入实机。无相机 USB/FF80 命令、无 RAM/Flash 操作、无修改 DAT、无可刷补丁。

## 1. 本轮找到的真实配置源入口

| 项目 | X-S10 3.11 | X-T4 2.12 |
| --- | --- | --- |
| 当前描述符头 | **0x02D987E8** | **0x02D0BF48** |
| 描述符载荷起点 +0x0C | 0x02D987F4 | 0x02D0BF54 |
| 主配置缓冲区指针字段 +0x10 | **0x02D987F8** | **0x02D0BF58** |
| 注册表选中记录载入器 | FUN_021F9194 | FUN_02165210 |
| 查找头部 / 查找载荷 | FUN_021F893C / FUN_021F8D64 | FUN_021649B8 / FUN_02164DE0 |
| 三处已验证上游调用函数 | FUN_021E6D48、FUN_021E6EA8、FUN_021E7138 | FUN_021512D4、FUN_02151434、FUN_021516C4 |
| 所用主配置缓冲区状态字节 | +0x04 | +0x04 |
| 所选类型 / 子选项 | **0x206 / 0x207**, 子选项 0x8C | 同左 |

这是运行时**配置记录类型**判断，不是 eModeMovieCodec、HEVC Profile、10-bit bit-depth 或传感器 FPS 枚举。上述调用链读取“当前缓冲区 +0x04”选择记录，并不读“当前缓冲区 +0x5B0”。两机基本同构，因此不能说这就是 X-S10 的机型特有限制。

示意（箭头表示已证实的**静态代码数据边**，并不保证所有环节同一次执行）：

~~~text
配置对象 +0xAC4 → 当前缓冲区指针 → [当前缓冲区+0x04]
                                 |
                     ==0 → 类型0x206
                     !=0 → 类型0x207
                                 |
                         固定参数 0x8C
                                 v
           X-S10 FUN_021F9194 / X-T4 FUN_02165210
                    /                       \
           头部查找                           载荷查找
               |                               |
           memcpy 12B                       memcpy 动态长度
               v                               v
         描述符 +0x00                       描述符 +0x0C
                                               |
                长度>=8 才完整覆盖描述符主指针字段 +0x10
                                               |
                 第27阶段：初始化器写入运行时 +0xAC4 指针槽
                                               |
                 第26阶段：当前配置缓冲区整块复制到 Recorder
                                               v
                                     Recorder 源 Codec (+0x5B0)
~~~

上述动态长度是否曾达到 8、记录中的指针值是否有效、初始化及复制先后顺序，都尚未从真实运行时得到确认。

## 2. 配置源记录地址和动态索引

利用原厂 Section2 little-endian PC-relative 常量，和 Ghidra 类型查找函数的返回值双重核对：

| 源记录字段 | X-S10 | X-T4 |
|---|---|---|
| 类型 0x206 动态记录头部基址 | **0x02D98A68** | **0x02D0C1C8** |
| 类型 0x206 动态记录载荷基址（头+0x0C） | **0x02D98A74** | **0x02D0C1D4** |
| 类型 0x206 动态记录索引计数变量 | **0x02D9C2A4** | **0x02D0FA04** |
| 类型 0x206 记录偏移 | (counter−1)×0x50 | (counter−1)×0x50 |
| 类型 0x207 固定记录头部 | **0x02D9B358** | **0x02D0EAB8** |
| 类型 0x207 固定记录载荷（头+0x0C） | **0x02D9B364** | **0x02D0EAC4** |
| **另有**类型 0x200 注册表头部 | 0x02D98838 | 0x02D0BF98 |
| 类型 0x200 注册表载荷 | 0x02D98844 | 0x02D0BFA4 |

0x206 的真实条目地址需要加上运行时索引，索引有效性和长度字段也待验证。0x207 使用固定记录。上一轮看到 0x200 记录存在，但本阶段找到的三处注册表载入器**直接调用者只传 0x206/0x207**，所以不能把 0x200 表项默认判成正在使用的 Recorder Codec 值。

## 3. 原始 ARM 验证：两机各七条，共十四条调用边

| 路径 | X-S10 BL 调用地址 → 目标 | X-T4 BL 调用地址 → 目标 |
|---|---|---|
| 模式选择上游 #1 | 0x021E6E60 → 0x021F9194 | 0x021513EC → 0x02165210 |
| 模式选择上游 #2 | 0x021E7060 → 0x021F9194 | 0x021515EC → 0x02165210 |
| 模式选择上游 #3 | 0x021E71DC → 0x021F9194 | 0x02151768 → 0x02165210 |
| 记录头部查找 | 0x021F91A8 → 0x021F893C | 0x02165224 → 0x021649B8 |
| 记录载荷查找 | 0x021F91BC → 0x021F8D64 | 0x02165238 → 0x02164DE0 |
| 固定头复制 | 0x021F91DC → 0x012A9148 | 0x02165258 → 0x01281848 |
| 变长载荷复制 | 0x021F91F4 → 0x012A9148 | 0x02165270 → 0x01281848 |

上述 BL 都直接从原始固件解码 A32 有符号相对位移，不仅依赖 Ghidra 函数名。前 3 条还对照 Ghidra 的 direct CALL xrefs；所有相关函数均反编译成功。

**目的地及长度的原厂指令细节**：
- X-S10 载入器 MOVW/MOVT R0 得 0x02D987E8，X-T4 得 0x02D0BF48；
- 第一次复制 MOV R2,#0x0C 为固定头 12 字节；
- 第二次复制的 LDR R2,[R4,#4] 来自**选中源头部 +0x04**，是不可静态推断的运行时长度；
- 第二次复制目标由 PC LDR 读原厂数据常量：X-S10 在 0x021F9218 含 0x02D987F4，X-T4 在 0x02165294 含 0x02D0BF54；
- 上游三处调用前均存在 MOV R1,#0x8C 和 CPY R0,R4；
- 两处独立的具体选择器直接验证 LDR [R3,#0xAC4] 和 LDRB [R3,#4]；第三处相同选择逻辑由真实 Ghidra C 证实。

**第29阶段与第28阶段并不相同**：第28阶段定位描述符的“16 条记录缓存备份/恢复”，本阶段定位“按类型 0x206/0x207，从模式注册表查找源记录并载入当前描述符”。两者虽都写相同结构，不能把两个路径想象为恒定顺序运行。

## 4. 对 Codec 问题的准确边界

描述符当前指针在 +0x10，复制载荷目标始于 +0x0C，二者差 4 字节；若欲完整覆盖整个四字节指针，载荷复制至少 8 字节。**目前未测得该长度、源记录中的真实指针值、指针对应的数据对象，也没有建立 GUI Codec 全局 0x01B88650 到缓冲区 +0x5B0 的写入链。**

因此，本阶段补充的是主配置缓冲区指针值可能来自哪一份模式记录的**静态来源机制**，不是已经恢复该缓冲区 Codec 字节的实际初值。HEVC Main10 bitstream、SPS bit-depth、4K60 传感器/ISP 和持续写卡同样完全未证明。无法提出可信的安全刷写补丁。

## 6. 下阶段关键目标

优先定位 **0x206 动态记录中 +0x04 的长度字段**、counter 范围和该记录载荷中被复制到当前描述符 +0x10 的四字节指针的真实生产者。检查 0x207 对应静态记录的字段写入者；然后追踪运行时指针所指向的数据缓冲区 +0x5B0/+0x5B1 的实际赋值，与 X-S10 的 GUI MovieCodec 设置 ID 建立或排除真正的关系。需要记住，静态“字段指针”和“字段值”是两种不同的证明对象。

**本阶段仅定位静态配置记录来源，10-bit / 4K60 尚未解锁。**
