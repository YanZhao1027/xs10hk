# 第46阶段：原厂96×64字节录像模式矩阵及4K59.94联合条件（2026-10-19）

**突破**：X-S10原厂3.11与X-T4原厂2.12存在完全相同的96×64字节Recorder模式记录表。各条记录通过真正的ARM查表调用，按模式类别、两字节分辨率键、帧率枚举和品质/变体字段进行**四条件同时匹配**，命中后调用独立的宽度与高度映射ROM表来构造VPU分辨率。两机原厂Section1/Section2固定SHA与只读Ghidra调用均已核对。静态矩阵中各含3条3840×2160 @59.94fps及3条4096×2160 @59.94fps条目。

**能力边界**：ROM内静态表项存在，不等于X-S10实体机允许该模式、UI可选、硬件传感器/ISP/V61支持、HEVC同时合法或录卡持续内录4K60。没有真实Main10 SPS、没有修改设备。本项目X-S10的离线ROM为3.11，实体机之前报告2.10。

## ROM解析器真实匹配逻辑

1. 当前Recorder的动态模式对象+0x5F5类别等于记录row[0]。
2. 当前Movie配置对象+0xADD8小端u16模式键等于row[1:3]。
3. 动态类别根据条件决定读取Movie配置+0x5C6或者+0x5C7作为fps枚举，必须等于row[3]。
4. X-S10 Movie配置+0x9B8（X-T4 +0x9BC）的变体/质量字节必须等于row[4]。

每次比较不满足则把指针加0x40处理下一条，到0xFF终止。命中后width函数使用表[1]作为行索引，表[2]为列索引0..3；表[2]其它值统一映射至第4列。对应height采用同样规则但使用独立ROM表。宽高结果分别写入Recorder运行时+0x602/+0x600；第45阶段MovieSetup从这里取编码分辨率。

Recorder初始化器建立Movie运行时+0x6018指针，按高速录像类别初始化+0x5F5后调用上述解析器；原始ARM BL计算与Ghidra直接调用xref一致。此静态查表器**不直接使用**MovieCodec+0xADDA作为第五个匹配条件；但不代表上游没有基于Codec禁用某些fps/分辨率组合，或者硬件真正支持该组合。

## 与先前HDMI 4K60记录的区别

第22阶段找到的HDMI EDID动态4K60接收器能力码（例如0xF0/0xF6）表示连接的显示设备能接收哪些视频格式，属于另一套协议。第46阶段的96×64表属于原厂Recorder内部Movie模式参数，在完整静态表内确有分辨率×fps联合键，但都不能直接替代传感器读出、ISP、V61和录卡端的实机证据。
