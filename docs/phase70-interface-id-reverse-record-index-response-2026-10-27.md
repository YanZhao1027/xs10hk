# 第70阶段：接口ID/子代码→记录索引的反向解析与0x61结果入队（2026-10-27）

## 核心新证据与严格边界

在第68–69阶段确认 **36条原厂接口描述符**、默认 `0xFF` 结束的候选索引列表和接收标记为 `0x302` 的运行时支持模式内容后，本阶段进一步在 **X-S10 3.11 / X-T4 2.12 的原厂ARM与Ghidra**找到一个真实的反向解析函数：拿已经由运行态接口选择器输出的**主接口ID/子代码**，在36条 ROM 描述符里找到相应**记录索引**，把该索引填进处理结果结构，并向通信队列提交一个通道参数为 `0x61` 的通知。

这首次把“动态支持接口ID、候选列表和被选择的描述符索引”与**同一条接口消息处理器的结果回传**接成连续的静态数据流。**不是GUI/Recorder的`0x20B/0x200`消息，也不是证明该通知抵达Movie模块，更不是 X-S10 已经录制4K59.94 HEVC Main10。**仍没有见到运行时接口ID/名单、传感器真实读出、ISP确认、VPU编码成功和最终Main10 SPS/录制文件。

## 1. 原厂记录的准确边界：之前+0x00接口ID其实是记录头+0x02

Phase69把接口ID字段的地址当成16字节记录的锚点（XS10 `0x0162DE0A`，XT4 `0x01605D2E`）。原厂反向解析器实际采用的记录**起始地址比它早2字节**：

| 字段/函数 | X-S10 3.11 | X-T4 2.12 |
|---|---|---|
| 真正的16字节记录起始地址 | **`0x0162DE08`** | **`0x01605D2C`** |
| 记录结束边界（36×16字节） | `0x0162E048` | `0x01605F6C` |
| 单条记录`+0` | 记录索引0…35 | 同左 |
| 单条记录`+1` | 分类辅助代码，业务含义未确认 | 同左 |
| 单条记录`+2` | 接口主ID | 同左 |
| 单条记录`+3` | 接口子代码 | 同左 |
| 单条记录`+4` | Phase69所称运行态门控字段 | 同左 |
| 单条记录`+12` | 24/25/30/50/60 数值字段 | 同左 |
| 反向解析函数 | **`FUN_01269520`** | **`FUN_0123F738`** |
| 解析器引用的运行态候选名单首址 | `0x01C856A3` | `0x01BE576F` |
| 引用名单地址的原厂 Section1 ROM指针字 | `0x01269630` | `0x0123F848` |

原厂两机36条记录的**首字节都恰好等于其记录索引**0..35，这是可直接核验的边界，不是从 `0x0A` 取值60推测而来。原厂均有完全一样的一对重复主ID97（记录22/23）和重复主ID102（记录34/35），**每对两条16B记录除首字节索引外的15字节内容完全相同**；主ID93的12/13也是相同结构。它们是**两个索引对应同一描述内容**，并非两个已证实的不同4K传感器时序或分辨率。

## 2. 精确的反向解析规则：候选名单是“成员资格”，不是排序第一优先

两机原厂函数C流程结构完全一致，A32/Ghidra均固定：

- 进入时将找不到匹配的哨兵初始化为 **`0x25`（十进制37）**，有效描述符索引仅0…35。
- 若子代码非零，先扫描全部36条，比较记录`+3`；之后若主ID非零，再扫描36条，比较记录`+2`。不应默认两项会在同一时刻都非零。
- 对每个命中的描述符，若此前完全未匹配则暂存首个有效行作为回退；随后检查**运行态候选名单是否包含该行的索引字节**。只要包含，该行就可以覆盖较早的返回值。
- 因为是**按ROM记录顺序**（索引升序）外层扫描，**反向解析器的重复ID候选最后一个“属于名单”的较大记录索引会胜出**。运行态名单里索引排列顺序不会改变这一反向解析结果。第69阶段的**正向候选选择器**则是逐个遍历候选名单找可用记录；两个函数的选择语义并不相同，不能混淆。

基于原厂记录内容、用原创逻辑**离线模拟**若干极小列表的对照（绝无设备执行）：

| 被查询主接口ID | 人工给定候选索引集合 | 反向解析器结果 |
|---|---|---|
| 97 | 默认名单`[11,10,9,8,7,5,4,0]`（不含22/23） | **22**：首个ROM ID97匹配作为回退 |
| 97 | `[22]` | **22** |
| 97 | `[23]` | **23** |
| 97 | `[22,23]` 或 `[23,22]` | **23**：取原厂ROM扫描顺序中最后符合成员资格的记录，而非名单顺序 |
| 102 | 默认名单（不含34/35） | **34** |
| 102 | `[35]` 或 `[35,34]` | **35** |
| `0xFF`（无相应接口主ID） | 默认名单 | **`0x25`** 无匹配哨兵 |

**这些是原厂反汇编语义的合成输入模拟。**它们不能告诉我们实体X-S10当前名单包含什么，更不能通过手动指定23/35推导4K60功能。特别是无匹配的`0x25`，本阶段只记录其作为返回值的静态语义；未证明硬件收到该状态后的内存安全性或实际异常。

## 3. 该结果在运行时接口消息处理器内被实际使用

| 已核验ARM静态调用边 | X-S10 | X-T4 |
|---|---|---|
| 处理标记`0x302`响应内容的函数 | **`FUN_0126B7E0`** | **`FUN_012419F8`** |
| 首先调用候选/支持ID选择器 | `0x0126B89C`→`FUN_0126B508` | `0x01241AB4`→`FUN_01241720` |
| 接着调用反向解析器 | `0x0126B8A8`→`FUN_01269520` | `0x01241AC0`→`FUN_0123F738` |
| Ghidra结果写入 | `*(char *)(iVar6-1) = index` | 同构 |
| 紧接读取所选ROM记录的另一元数据字节 | `(&DAT_0162DE0F)[index*0x10]` | `(&DAT_01605D33)[index*0x10]` |
| 最后向`0x61`队列提交结果通知 | `0x0126B910`→`FUN_012A6084(0x61,...)` | `0x01241B28`→`FUN_0127E784(0x61,...)` |

**这几条BL真实存在于Section1 A32**，不是仅根据Ghidra反编译字符串或字符串出现判断调用。消息处理器根据当时运行态条件先完成一系列响应解码和候选选择，符合其路径时才进行上述解析和提交；原厂直接xref没有证明该处理器在研究机身每次录像时都会执行。这里所谓“0x61消息入队”也**不是**证明下游最终收到了通知或确实把此值传给Movie录像模块。

## 4. 对4K60/Main10研究的实际影响

与第67–68阶段记录的`class0 + 4K像素键7 + 画幅2/7 + 普通FPS6 + BPS1/2/3 → 2160P静态表项`相比，这里的**接口记录索引0..35**和**Movie录像模式矩阵行0..95**完全独立。目前原厂只有这条**接口ID→记录索引→0x61通知**的实证，尚缺“0x61通知的下游所有者/控制流与Movie输入对象/传感器ISP时序”的正向边。静态ROM里重复的97/102并不证明传感器能真正读出2160P60；反过来默认名单没有97/102也不能证明硬件绝不支持。

下一阶段应优先确认 `0x61` 队列事件的实际**接收者/解码者**以及是否有跨模块数据流进入 Movie对象或 sensor/ISP 配置；或从选择器的接口ID映射到真实宽高、行/帧时间与buffer规格。没有这些证据就不应输出刷写补丁或解锁结论。

## 5. 可复验、测试及严格非侵入性

`tools/audit_stage70_interface_reverse_resolver_response.py`先重跑第69阶段及之前所有原厂SHA绑定审计，再核实两机Section1原始记录首字节序号、重复ID载荷、活动候选RAM指针ROM字、解析器两次16B步进与ID/子代码比较、成员资格、回退哨兵，以及响应处理器三个按顺序的原始A32 BL和Ghidra数据存储/队列提交。`tests/test_audit_stage70_interface_reverse_resolver_response.py`只生成**完全人工A32、伪Ghidra函数、合成接口列表与描述符**，包括反向列表次序与重复ID优先规则、缺失哨兵/错误调用目标/变异字段的负测试。没有完整私有日志或厂商原始固件字节。

原始富士Section1/2、Ghidra项目与反编译全文只存在用户授权Ubuntu Git忽略`output/`内。研究机固件X-S10 3.11和X-T4 2.12，之前用户实体X-S10为历史FW2.10，ROM地址不能直接用于实体设备。**本阶段仅离线只读：无相机、USB/FF80、实时设备RAM/Flash、ROM/DAT写入、补丁、签名修改或刷写。**
