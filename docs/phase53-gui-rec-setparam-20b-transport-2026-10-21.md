# 第53阶段：从GUI `+0x581/+0x5B0` 真正追到整块配置快照与 `rec_setparam`/`0x20B` 消息排队请求（2026-10-21）

> **取得新的上游正向数据流实证**：在原厂 **X-S10 v3.11 / X-T4 v2.12** 中，GUI录像配置对象的起始地址真实作为函数参数提交给 `rec_setparam` 路径；该路径在原始ARM中以GUI为第二个实参，将 **0x5DC/0x5D8字节**复制到独立发送暂存RAM，再构造带 **`0x20B`类型、目标模块7、8字节消息体**的控制头，调用原厂队列提交函数。第52阶段确定的 `eMode4kOut` `+0x581` 与 `eModeMovieCodec` `+0x5B0` 均被这些整块快照覆盖。**发送进队列的消息体是8字节（暂存数据指针+关联值），而不是1500字节内嵌载荷。**
>
> **关键缺口仍在**：没有独立解出模块7接收侧队列领取/反序列化，并证明该8字节指针恰好经过有效转发，成为Recorder `type=0x20B`描述符的`+0x0C`载荷指针，或者变成当前 `type=0x200` 初始化时读取的`P`。`0x20B`注册表和消费代码确实存在，**但共享类型编号不自动构成跨线程、跨服务已投递证明**。当前P真实运行地址、最初`P+0x581`/`P+0x5B0`值、Main10 SPS、4K60内录均未知。

## 4. 独立消息包装：确实是`0x20B`和8字节消息体，不是全长Inline

| 项目 | X-S10 原始ARM | X-T4 原始ARM |
|---|---|---|
| `MOVW R3,#0x20B` + `STRH` 保存消息标识 | `0x02197F4C / 0x02197F50` | `0x020EAFA8 / 0x020EAFAC` |
| 将值`7`放进消息头参数 | `0x02197F5C / 0x02197F60` | `0x020EAFB8 / 0x020EAFBC` |
| `MOV R3,#8` + 记录长度字段 | `0x02197F64 / 0x02197F68` | `0x020EAFC0 / 0x020EAFC4` |
| 8字节子结构第一个字 | 暂存区地址`R5` | 同左 |
| 子结构第二个字 | 由调用方提交的`0x20C0000`类别序号产生器返回值 | 同左 |
| 准备排队请求参数、提交BL | `0x02197F74 / **0x02197F78**`→`FUN_012A6084` | `0x020EAFD0 / **0x020EAFD4**`→`FUN_0127E784` |

原厂通用排队函数先检查参数长度、申请消息缓冲、逐字保存头部，再按所提供长度从外部源指针复制消息体；随后调用映像外的系统函数实现进一步排队。它能证明原始代码**尝试提交8字节消息载荷**；能否成功、队列深拷贝的具体时机、8字节中指针所指暂存区是否在接收时仍有效，属于没有实机/系统侧证据的问题。**不能把“发送方完整内存快照”当作“队列消息内嵌完整配置”**，也不能声称本次的GUI数据已抵达Recorder主输入P。

## 5. 另一端找到了Recorder自己的`0x20B`注册表和条件复制处理器

| Recorder独立代码证据 | X-S10 | X-T4 |
|---|---|---|
| 通过`0x20B`分派的注册表头 | **`0x02D98928`**（ROM literal `0x021F8D5C`） | **`0x02D0C088`**（literal `0x02164DD8`） |
| 同类型注册表载荷，头+12B | **`0x02D98934`**（literal `0x021F9128`） | **`0x02D0C094`**（literal `0x021651A4`） |
| 对应查表函数 | `FUN_021F893C / FUN_021F8D64` | `FUN_021649B8 / FUN_02164DE0` |
| 按描述符type==`0x20B`决定是否整块复制的函数 | **`FUN_0221C934`** | **`FUN_02189348`** |
| 描述符头基址 | `0x02D987E8` | `0x02D0BF48` |
| 先校验`type==0x20B`的原始MOVW/CMP | `0x0221C95C/60` | `0x02189370/74` |
| **有条件的源指针** | `[descriptor+0x0C]`，槽`0x02D987F4` | `0x02D0BF54` |
| 从描述符`+0x0C`取源指针的原始ARM `LDR` | `0x0221C9E4` | `0x021893F8` |
| memcpy完整记录的原始ARM BL | `0x0221CA04` | `0x02189418` |
| 源长度 | `0x5DC` | `0x5D8` |

在同一Recorder处理函数前部还有 `Qslot = Pslot` 的运行时指针值转存（与第50阶段的指针别名问题相关），**但0x20B有条件的这个memcpy，源是“描述符+0x0C中的指针”而非直接`Pslot`。** 两者不能相互替代，更不能仅凭同类型0x20B假设它们必然是同一个GUI源数据指针。

还有一个重要的相邻却不同的流程：第27/52阶段 `FUN_02214738` / `FUN_02180D0C` 从描述符 `+0x10` 初始化当前P槽时，**严格要求type==`0x200`**；而上述接收候选要求type==`0x20B`。单一时点的描述符不能同时满足两个比较，时序、复制、回滚或消息切换必须另有已验证的机制才可联通。

## 6. GUI另有正常整块备份/恢复，但仍不是Recorder P

Ghidra `FUN_0114F164`（X-S10）/`FUN_0112373C`（X-T4）各自直接通过原始Section1 `MOVW R2,#0x5DC/#0x5D8` 调用同一memcpy；`FUN_0116B61C` / `FUN_0113FB3C` 根据方向参数让GUI与其它指针所指数据执行**双向整块备份/恢复**。这些是真实的GUI结构复制，不是阶段52已经排除的memcmp/hex dump；不过恢复指针来源属于另外的配置备份对象，当前**没有**证明它与Recorder P相等。这说明按“同样大小的memcpy”搜索会得到多个真实但互不相同的通道，必须追源/目的身份。

另外针对原始Section2符合MOVW立即数`0x20B`的**有限静态筛选**，X-S10得30个对齐字，X-T4得31个；在Ghidra中其中多个是纯类型判断、配置类别映射或缓存整理。筛选涵盖直接MOVW，**不是包含从参数/间接表产生20B的全固件穷举**，也不证明这些函数中有一个就是模块7接收解码器。
