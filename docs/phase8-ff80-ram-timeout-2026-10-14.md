# 第八阶段：X-S10 FF80 RAM 读取实验失败与安全暂停（2026-10-14）

> **安全警告：不要在 X-S10 上重复运行 RAM 读取实验。实机在首次读内存请求后停止响应 FF80；随后恢复调试开关的通信失败。**
>
> **机主已确认：拨到 OFF 时红灯仍亮；打开电池仓后红灯熄灭，取出电池再装回后，X-S10 能正常开机。** 这说明此次异常并未导致持续无法启动的永久性变砖。完整拍摄、视频录制及长期稳定性尚未专门验证；调试状态在断电前未能通过 USB 确认恢复。

## 用户授权与最小化设计

机主知晓 FF80 协议的实验风险，同意在受限条件下尝试内存读取。本实验通过用户授权的 Ubuntu 连接 FF80 进行；不访问私有照片、持久化 EEPROM 保存、固件更新、校准或任意代码执行。

此前已在 X-S10 上完成 FF80 型号/版本查询（型号 X-S10，FF80 版本标签 1.60，普通 PTP 版本 2.10），并只读确认配置偏移 0xF7 为 0。

根据 [fffw Route 0xff80 笔记](https://github.com/tiredboffin/fffw/wiki/Route-0xff80)，作者展示过以地址 0x00000000 为起点的 RAM 读取，且说明 FF80 `cfgdata` 写入先修改 RAM，持久化需要另外执行 EEPROM 保存命令。然而该笔记**没有证明 X-S10 的地址 0x00000000 可安全读取**。这次实验不应推广为成功的机型移植案例。

## 完整实机结果

实验首先保持调试关闭，以只读请求访问固定地址 0x00000000 的 **16 字节**，收到：

~~~text
READ_DENIED: firmware returned 0x1/0xffff
~~~

该阶段没有任何配置写入。FF80 仍连接，且单字节只读复查确认 0xF7=0。

然后由受限脚本 `tools/ff80_ram_sample.py` 执行：

1. 重新确认 FF80 USB VID:PID `04cb:ff80` 和产品型号 `X-S10`。
2. 读取确认 `0xF7=0`。
3. 用 `cfgdata` 写入子命令 3 在 RAM 配置区中临时将单个字节 `0xF7` 写为 `1`。**这是本次唯一允许的相机配置修改**，没有调用 EEPROM 保存。
4. 用 `cfgdata` 读取子命令 2 **再次确认 `0xF7=1`**。
5. 发送 FF80 RAM 读取命令 `0x00200001`，子命令 `2`，固定起点 `0x00000000`，读取长度 **16**。

在第 5 步请求答复时，**USB 控制传输（D1）超时**：`[Errno 110] Operation timed out`。

脚本的异常清理中，两次尝试将调试配置 `0xF7` 恢复为 `0`，均遇到 USB 超时；会话关闭也超时。随后开启新的独立会话读取 `0xF7` 时，USB 返回 `[Errno 5] Input/Output Error`。操作系统在最后仍能在 USB 描述符层面看到 `04cb:ff80`；但 **USB 枚举成功并不代表维修程序还在响应**。

**没有返回任何 16 字节 RAM 数据；没有成功生成本地 RAM 样本文件。** 没有执行全内存扫描、写入任意 RAM 地址、EEPROM 保存、固件更新、代码注入或工厂校准指令。

## 已知与未知

| 判断 | 证据状态 |
| --- | --- |
| `0xF7` 曾暂时设置为 1 | **确认**：设置后立即读回 1 |
| 内存地址 `0x0` 安全或映射为 RAM | **未证实**：来自不同机型的通用文档示例 |
| 内存读取成功 | **否**：USB 超时，没有样本 |
| `0xF7` 已恢复 0 | **未确认**：恢复命令超时 |
| EEPROM 或固件被改写 | **没有执行相关命令** |
| FF80 协议在读请求后响应正常 | **否**：服务会话、后续查询均失败 |
| 机身可以重新正常开机 | **已由机主确认**：打开电池仓后指示灯熄灭，取出并重新安装电池后正常开机；尚未验证全部功能 |

**不要将该现象直接归因为读到了 MMIO、RAM 地址不合法或 FF80 不兼容。** 这些都是可能的解释，也可能还有其它原因。尚无足够的调试证据。

## 机主实际恢复结果

机主报告：将电源开关拨至 OFF 后，红色指示灯仍保持亮起；随后在打开电池仓时指示灯熄灭。机主取出电池、重新安装，**X-S10 随即正常开机**。该结果与运行时程序死锁、通过完整断电重启恢复的情况一致，但不能据此判明最初导致死锁的准确原因，也不能单独证明一切相机功能均已正常。

本次没有执行 EEPROM 保存、固件刷写或校准写入。根据公开源码说明，临时修改的 `0xF7` 运行时配置理论上会随完全断电丢失；由于不再进入 FF80，该值**不做再次实机读取验证**。严禁为了读取或验证该位而重新开启诊断模式。

## 当前处置建议

1. 停止一切 FF80 协议访问，不要反复尝试其他 RAM 地址、USB 调试指令或固件更新。
2. 机主在确认没有固件更新/存储写入进行中的情况下，把电源拨到 OFF，断开 USB，等待约 10 秒，正常开机。
3. 如无响应，在 OFF、USB 已断开的情况下卸下电池，等待约 30 秒后重装，**只尝试一次正常开机**。该措施主要针对可能的暂时性死机；不能保证恢复未知硬件故障。
4. 如恢复拍摄功能，确认菜单与 SD 卡正常，不在现场再进入 FF80；后续研究以纯离线固件为主。
5. 如仍不能正常开机，停止后续试验，考虑联系富士官方维修，不自行刷不匹配固件或盲目恢复出厂设置。

## 代码紧急禁用

GitHub 仓库保留 `tools/ff80_ram_sample.py` 供审核失败路径，但主入口现已**强制退出**，防止未经修改直接再次对实机运行。之前的模拟测试（共 38 项）只能证明 Python finally 分支在**模拟 I/O 异常**中会尝试恢复；不能保证实际 USB 固件死锁时恢复指令能送达。以此次实机观测为准。

**机主已确认普通开机恢复；即便如此，后续不再使用 Remote Desktop Commander 与相机的 FF80 接口通信**。对 GitHub、静态二进制分析与脚本审查可以继续。
