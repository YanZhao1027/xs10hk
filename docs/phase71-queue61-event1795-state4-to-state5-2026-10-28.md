# 第71阶段：接口响应的0x61队列接收任务、事件表第7行与状态4→5闭合（2026-10-28）

## 核心突破与准确适用范围

本阶段对 Fuji **X-S10 v3.11 / X-T4 v2.12** 的原始 X6 ROM 及只读 Ghidra 同时验证：第70阶段“接口ID解析→结构结果→队列0x61发送”的**同一原厂0x61队列**具有明确的任务注册、接收循环、按事件ID及运行态列分派的静态事件表。发送者将当前状态设为**4**并发送事件 XS10 **0x1795** / XT4 **0x17A7**；事件接收者按序号检索、用当时的状态索引选择回调；第7行/状态4槽恰好指向使状态成为**5**、重新选择接口候选并触发下一控制请求的函数。

因此“发送者→队列→接收任务→事件查表→状态4的回调→状态5的接口控制”在**原厂静态ARM+ROM/Ghidra的条件化**层面已经闭合。这比仅发现一个队列或字符串强得多；但是用户实体X-S10历史固件2.10与研究样本3.11不同，且**OS任务创建、每次消息发送/成功接收、状态不被抢先修改、最终硬件生效仍不具备运行时证据**。`0x61`是此处通信/任务队列编号，和GUI→Recorder使用的模块7、事件类型`0x200/0x20B`不是同一协议对象。没有HEVC Main10 SPS和4K59.94的实录文件。

所有上述指定直接BL目标在本阶段**从原始Section1机器字重新解码**核验，非仅凭反编译或文本出现。两个原厂事件矩阵的查表地址均使用**每行`0x1C`（7×4B）**；每行先有1个事件ID，再有6个动态状态槽。接收循环中的指针公式相当于：`table+4+(event_row*7+current_state)*4`。对发送事件而言**row=7、state=4**，指针恰好指向上述状态5回调；第7行其余5个状态槽为0。因此**状态字段仍为4是本条明确的分派前置条件**。如果状态提前改成5或其他值，不会进入这个表格单元中的处理函数。

接收循环还明确处理`FUN_012A62D0` / `FUN_0127E9D0`失败及返回`-0x32`等情况，注册/队列提交封装器也可能失败。故**机器码中的条件分派不是对某次实际硬件执行成功的保证**，更不能把“队列入队函数被调用”写成“当前相机确实收到了事件”。

## 第69–70阶段的结果在状态5后如何被使用

状态4回调不仅将状态写成5，还**清零多组重试计数/标志**，调用已在第69阶段追踪的接口优先级/候选选择函数（XS10`FUN_01269B80`、XT4`FUN_0123FD98`）。它们所见的`0x3840/0x3841`选择条件和运行时名单仍属于**接口/传感器模式协调域**，不是第46/67阶段的Recorder四参数矩阵。根据独立的状态标志，该回调从请求码`0x13`或者两机不同的`0x80D9/0x80D8`中选择一项继续通知其他控制层。

另外，在独立的接口驱动/初始化函数XS10 `FUN_0126C388` / XT4 `FUN_012425A0`中，可以看到**状态==5**的检查以及接口/FPGA控制函数的后续调用；它们还涉及队列/模块 **`0x35` (XS10) / `0x37` (XT4)**。这说明静态ROM还存在下一步控制代码，但**目前尚未证明状态5回调直接启动了该函数，或这些队列中的控制消息等于最终传感器/ISP/VPU录制成功回执**。也没有证据将任一36条接口记录索引直接映射到96行Movie 2160P/FPS6 LUT。

- `tests/test_audit_stage71_queue61_event_task_state_dispatch.py`：**102项**完全人工生成的ARM分支、事件矩阵、伪反编译文本、不同状态列和故意破坏顺序/指针/事件值的正反例，无原厂固件内容或Ghidra全文。
