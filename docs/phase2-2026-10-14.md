# 第二阶段：X-S10 视频编码固件模块与 Ghidra 静态分析（2026-10-14）

## 范围与关键结论

**仅在 Ubuntu 主机上分析从原厂 DAT 解码的本地副本。相机固件及 SD 卡均未被更改。**

现阶段能够证明固件包中包含多个视频编码器/解码器相关的描述符和调试字符串，但不能证明 X-S10 可以实际启动 HEVC Main10 或 4K59.94 视频录制。更不能根据这些文本做机身刷写补丁。

原始固件 SHA-256：`141e8c3882dd456d3b954fd1dd3681b86e7d001f617dca2fb8d8dfd4f7eede53`（DAT 3.11）
负载 SHA-256：`e8fc52da295bc81cd764c0e6f5438b12e3e743a5222e62597b6a58e1ed2f44da`

## 三组实际存在的编码模块描述符

使用 `tools/module_inventory.py`，在解码负载中找到三组符合相同前缀格式的记录：

| 文件偏移 | 观察到的名称 | 说明 |
| --- | --- | --- |
| `0x02DA0060` | `56610002H.265 MP Encoder` | HEVC 编码相关区域 |
| `0x02E08060` | `56610002H.264 BP/MP/HP Encoder` | H.264 编码相关区域 |
| `0x02E41060` | `56610002H.264 BP/MP/HP Decoder` | H.264 解码相关区域 |

三处记录的起点均带有字节前缀 `5e eb 00 00 04 02 00 00`。记录描述中 `56610002` 开头可能为厂商内部模块版本/标识，**暂未证明具体语义**。

其它可用定位点：
- `HEVCENC`：`0x02DA00A0`；
- `set-opt encode stream bitdepth: unsupported value`：`0x02DAE0F8`；
- `Firmware version does not match hardware!`：`0x02DAE2ED`；
- `4K_59_94P_400M_16`：`0x00A37CC7`。

上述偏移都是 *payload 文件偏移*，不是运行时虚拟地址，也不能据此判断模块是否被启动。「MP」可能对应 HEVC Main Profile，但没有从功能路径确认 profile/10-bit 支持范围。

复现：
~~~bash
cd /home/zyubuntu/xs10hk
python3 tools/module_inventory.py output/xs10-payload.bin
python3 tools/video_markers.py output/xs10-payload.bin
python3 -m unittest discover -s tests -v
~~~
输出的 JSON 放在被忽略的 `output/` 下，不提交原厂字节或存储卡信息。

### 已验证的 ARM 指令解码

从 payload `0x00200000` 提取 128 KiB，Raw Binary 导入 Ghidra，配置 `ARM:LE:32:v7`，基础地址 `0x00200000`，用 `ghidra_scripts/ARMProbe.java` 验证。

起始指令：
~~~text
00200000 mov r1,#0x58
00200004 mov r0,#0x2
00200008 bl 0x005757a0
0020000c mov r4,#0x19
00200010 b 0x001fea10
~~~

**重要限制**：`0x005757A0` 在 flat 映射中呈现非典型指令模式，自动反编译出现错误数据路径。说明该原始负载并不能未经确认就当作一段连续、基址为零的 ARM 运行映像；应优先重建段加载关系。

### 全区域试验：结论不应过度解释

用 `xs10-arm-main-first16m.bin`（payload `0x00000000..0x00F9FFFF`，16,384,000 字节）尝试 Raw Binary 导入和自动分析：

- Ghidra 12.1.4 / ARM:LE:32:v7；
- 两个可信度相对更高的入口附近有合法 ARM 指令；
- 自动分析得到了 **2242 个“候选函数”**，其中包括错误将数据当代码的区域；不是有效函数数量的验证；
- 对 `H264`、`H265`、`4K_59_94P_400M_16` 等所探测的目标偏移，现有项目 **没有形成可信的交叉引用**（查询结果为 0）；
- 因此**尚未证实**由主固件调用 HEVC 编码器，也未找到确凿的 X-S10 4K60 控制分支。

本地 Ghidra 项目（不上传）：

- `output/ghidra/xs10-arm-probe.gpr`
- `output/ghidra/xs10-arm-main.gpr`
- `output/ghidra_main_stdout.txt`（有 Ghidra 自动分析的错误提示）

## 有参考价值的社区资源

- [FujiHack 官网](https://fujihack.org/) 和 [原厂固件格式说明](https://wiki.fujihack.org/firmware/)。

- [X-T4 固件 2.12 的 V61 syscall 名称表](https://github.com/tiredboffin/fffw/blob/main/ffun/ports/xt4/0212/v61_syscalls.h) 包含 `DRV_INIT`、`DRV_SET_ENC`、`DRV_SET_DEC`、`DRV_STOP` 等枚举；可作为未来找到 X-S10 调用链的参考，不能直接视为两机功能相同。

## 下一步优先级

1. **先重建内存映射**：确认 X-S10 固件文件头、分段、压缩机制和运行时装载地址，避免 flat Ghidra 导致假交叉引用。
2. **HEVC 与 H.264 模块静态比较**：定位位深/profile 选项、模块版本和硬件校验，并与合法取得的 X-T4 官方固件相同区域做哈希及结构差异比较。
3. **视频模式状态机**：有正确 ELF/内存映射后追踪 `4K_59_94P_400M_16` 到录制设置函数/传感器读取路径，查证而不是猜测。
4. **仍不触碰相机固件**：无针对 X-S10 的经过验证的恢复路径之前，不尝试魔改刷写；本阶段也不调用厂商私有 USB 服务指令。

**法律/许可提示**：富士官方固件下载协议含逆向相关限制；研究前需自行检查适用条款与所在地法律。本仓库只保存研究工具、标记及偏移说明，不提供原厂固件或衍生完整二进制。
