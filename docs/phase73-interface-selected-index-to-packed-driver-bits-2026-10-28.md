# Phase 73 — 接口记录索引真正进入驱动命令位字段；0x302应答门与初始化轮询（2026-10-28）

## 结论与证据级别

本阶段对**X-S10 3.11 / X-T4 2.12 原厂X6 ROM和只读Ghidra**再推进了Phase70–72的关键断口：来自接口ID/子代码的反向解析结果**实际被写入同一个RAM记录索引字节**；另一路独立的驱动初始化函数**读取该索引**，拿它访问第70阶段同一36×16B ROM接口记录的**相对偏移`+0x08`**，形成一个值为0或2的**驱动配置字节**，通过两层包装器合并到命令上下文的**`+0x624`字第20–21位**。两机这些条件、RAM别名、原厂直接ARM BL、Ghidra xrefs均对照吻合。

同时，上一阶段另一条就绪标志XS10 `0x01C84FB4` / XT4 `0x01BE5080`的**至少一条正向写入来源**已定位于`0x302`运行时数据包的某个`type3`项目，且该标志在初始响应分支有明确清零。下游还有**至多42轮带延迟的就绪轮询**，失败返回`-0x32`。这首次将**接口身份选择→真正参与驱动上下文字节的配置**和**特定应答标记→硬件初始化必要状态门**串起来，但绝不等于实际传感器4K59.94读出、录像分辨率、HEVC Main10输出或硬件已初始化成功。

## 1. 反向解析结果复用同一RAM字节，而非跨模块猜测

| 证据 | X-S10 3.11 | X-T4 2.12 |
|---|---|---|
| 0x302接口响应处理器 | `FUN_0126B7E0` | `FUN_012419F8` |
| 原厂ROM中响应数据字指针 | `*(uint32_t *)0x0126BDB8 = 0x01C84F8A` | `*(uint32_t *)0x01241FD0 = 0x01BE5056` |
| 反向解析结果实际写入 `(data_ptr-1)` | **`0x01C84F89`**；原始写入指令`0x0126B8AC` | **`0x01BE5055`**；指令`0x01241AC4` |
| Phase72驱动消费同一索引 | `FUN_0126C388`；原始索引读指令`0x0126C888` | `FUN_012425A0`；`0x01242AA0` |
| 真正36条×16B接口记录起始 | `0x0162DE08` | `0x01605D2C` |
| 驱动字段地址 / 机器码读指令 | `0x0162DE10 + index×0x10`；`0x0126C890` | `0x01605D34 + index×0x10`；`0x01242AA8` |

Phase70原始解析器XS10 `FUN_01269520` / XT4 `FUN_0123F738`在**符合相应响应处理分支时**返回记录索引0–35或不匹配哨兵`0x25`，源处理器保存到上述RAM字节；Phase72的驱动**在另一个独立的启动条件分支**按当前RAM字节读取接口描述符。这个RAM字节还存在其它原厂写者，且`0x61`队列、调用顺序、抢占及记录索引值都未在实体设备上观察到。因此是**条件式静态内存数据流**，不是一次已实际运行的完整事务。尤其是**`0x25`并非合法的36行索引**，目前不声称在该哨兵出现时下游一定安全或一定调用。

## 2. 同为“数值60”的两组接口记录，命令位字段确实不同

原始36条接口描述符的`+0x08`字段在**0–23号索引均为0，24–35号索引均为1**，两机576字节表完全同构。此前确认的八条`+0x0C`数值60记录，本阶段核验的派生配置为：

| 接口主ID | 接口描述符索引 | 描述符`+0x08` | 条件分支生成的`local_68` | 在命令上下文`+0x624`字产生的第20–21位值 |
|---|---|---|---|---|
| 3、4、5、16 | 0、3、5、11 | 0 | 2 | `0x00200000` |
| **97** | **22/23** | **0** | **2** | **`0x00200000`** |
| **102** | **34/35** | **1** | **0** | **`0x00000000`** |

原厂C及调用关系：

1. 仅在共享状态等于5、随后特定就绪标志等于1的驱动路径中，函数XS10 `FUN_0126C388` / XT4 `FUN_012425A0`通过`ROM[index*16+8] == 0`设定`local_68 = 2`，否则`local_68 = 0`。同一函数读取`ROM[index*16+4]`的另一门控也存在，但尚无运行值证据。
2. XS10原始BL `0x0126C944`→`FUN_0126D1FC`，XT4 `0x01242B5C`→`FUN_01243414`，把`&local_6C`（包含`local_68`的第5个字节）作为第三指针参数传入命令构造器。
3. 构造器分别在原始BL **`0x0126D240`** / **`0x01243458`** 将这个第三参数传入 XS10 `FUN_0126F050` / XT4 `FUN_01245268`。后者计算中含`(param_2[4] & 3) << 0x14`并把合成字写入**软件命令上下文偏移`+0x624`**；另有软件镜像字X-S10`0x01823E60`、X-T4`0x01793074`。
4. 构造器随后在原始BL **`0x0126D298`** / **`0x012434B0`** 调用XS10 `FUN_0126E804` / XT4 `FUN_01244A1C`，后者执行与上下文中多个字段相关的**最多15段数值范围搜索及类别码判别**；无匹配时返回`0xFFFFFFFF`，匹配时更新上下文`+0x828`并返回0。上层驱动处该构造器调用的返回值在反编译结果中没有直接条件使用，不能把这处返回0视为硬件接收或录制成功回执。

**重要：**命令上下文`+0x624`的第20–21位**不是已证实的实体MMIO硬件寄存器或4K开关**；上述模式值也**不是**传感器实际宽高/帧时序或编码器Profile。对比X-T4固件与X-S10固件得到的是代码结构与静态选择差异，而不是实机结果。

## 3. 第72阶段“第二就绪标志”的原厂写入条件与轮询

- 接口响应处理器在首段响应分支**清零**就绪标志。处理标记为`0x302`的响应时，若存在**类型组3 (`bVar3==3`) / 子类型3**且后继两个签名字节分别为`0x0C`、`0x00`，则原厂**将就绪标志写为1**。在Ghidra C语义中该赋值出现在`(flag=1, 7<uVar14)`逗号表达式内，因此**赋值发生在附加长度条件判断之前**；仅扩展字段解析需要`uVar14>7`。不可错写成“长度>7才把就绪标志置1”。RAM另有其它写者，且未见实机应答内容。
- 仅有该应答标记还不够：Phase72外部设置路径仍须前置调用成功且`param_2==0`，并在下游状态为5和该标志为1时才走对应驱动分支。
- 该驱动在合成命令上下文之后调用就绪轮询XS10 `FUN_0126B018` / XT4 `FUN_01241230`（原始BL `0x0126C96C` / `0x01242B84`）。此函数每次轮询XS10 `FUN_0126DA5C` / XT4 `FUN_01243C74`；只要得到0就返回0，否则每次调用延迟函数参数5，最多**`0x2A`（42）轮**，穷尽时返回**`0xFFFFFFCE`（-0x32）**。
- 下一层原始轮询根据上下文标志选择`0x9500`或`0xFF00`来查询底层状态。**没有实际执行、记录真实返回值，也没有证明返回0时对应2160P60或Main10编码链成功。**
