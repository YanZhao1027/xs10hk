# 第三阶段：X-S10 3.11 与 X-T4 2.12 固件对照（2026-10-14）

## 结论

在这两个指定版本的固件中，**三个视频编解码器候选区域逐字节一致**，但两机的 H.265 / 10-bit 4:2:0 菜单文本明显不同。这是共享编解码器固件内容的证据，**不是 X-S10 已经能够启用 HEVC、10-bit 内录或 4K60 的证据**。

全部工作仅在 Ubuntu 上对本地原厂 DAT 副本进行只读分析。没有刷写相机，也没有上传原厂二进制。

| X-T4 | `FWUP0024.DAT` | 2.12 | `853d273b5603d3a2b93493f0ebd6a762b0b4b6bdc70317777775ae5f8ed93bc5` |

- X-S10 `output/xs10-payload.bin`：51,081,248 字节，SHA-256 `e8fc52da295bc81cd764c0e6f5438b12e3e743a5222e62597b6a58e1ed2f44da`
- X-T4 `output/xt4-payload.bin`：51,277,748 字节，SHA-256 `0d5bb9455d201c2a23ea2440b9c028f790ce3ef48ed252a632f5a99852593cac`

哈希只是文件指纹，不是厂家签名认证或校验和验证。这两个固件的版本不同，不能视为完全相同条件的对照实验。

## 编解码器候选区域的逐字节对比

以 X-T4 文件偏移为基准，X-S10 相同内容的文件偏移是 **+0x160000**。

| 编解码器候选块 | X-T4 起止偏移（右端不含） | X-S10 起止偏移（右端不含） | 字节数 | 不同字节 |
| --- | --- | --- | ---: | ---: |
| H.265 / HEVC 编码器 | `0x2C40000–0x2CA8000` | `0x2DA0000–0x2E08000` | 425,984 | **0** |
| H.264 编码器 | `0x2CA8000–0x2CE1000` | `0x2E08000–0x2E41000` | 233,472 | **0** |
| H.264 解码器候选块 | `0x2CE1000–0x2CF5000` | `0x2E41000–0x2E55000` | 81,920 | **0** |
| **合计** | — | — | **741,376** | **0** |

SHA-256（每一对完全一致）：

- H.265：`9d986c77d71a57ceefbd6b0bde2668f1a057f6892daff3be0fb4a4a3c5f4441c`
- H.264 Encoder：`3baf997561ea106e831bd9107acb7476997492a36df886dedfe275fb31c74243`
- H.264 Decoder：`58ec013d91c20f673f55131fc43840d8a65d8c72fb63dff76f9846547bac9508`

另外，按 64 KiB 块检查，X-T4 `0x2C00000–0x2E60000` 以及 X-S10 `0x2D60000–0x2FC0000` 这一大片相应范围也一致，但其中包含填充区域；**不能将 2.49 MiB 全部认定为编解码器微码**。

> 注意：上述“块”是根据记录特征和相邻描述符划分的实验性文件范围，尚未证明各模块真实的加载大小或运行时基址。

## 机内视频菜单文本资源（UTF-16LE）

通过对解码负载的精确字节序列计数，得到：

| 文本 | X-T4 2.12 | X-S10 3.11 |
| --- | ---: | ---: |
| `H.265` | **105** | **0** |
| `H.265(HEVC)` | **70** | **0** |
| `4:2:0 10bit` | **23** | **0** |
| `4:2:2 10bit` | 69 | 46 |

重复数量受多语言和资源复制影响，不能直接当成功能数量。X-S10 中的 `4:2:2 10bit` 标记与其 HDMI 外录能力相符。

两份固件也都能检出 ASCII 字符串 `4K_59_94P_400M_16`；其用途仍未知，不能当作 4K60 已在 X-S10 上使能的证据。

复现：

```bash
python3 tools/video_markers.py output/xt4-payload.bin
python3 tools/video_markers.py output/xs10-payload.bin
python3 -m unittest discover -s tests -v
```

## 目前最有依据的研究假设

1. **内录 10-bit：** 既然 X-S10 固件包含与 X-T4 二进制一致的 HEVC 候选组件，下一步优先对比主程序的编码器加载、硬件版本判断、像素格式及 Main10/profile 设置，而不是直接更改界面菜单。
2. **4K60：** 模式名称在两机固件中都存在，但传感器读取时序、视频处理管线、时钟/功耗和存储/散热仍需分别验证。
3. **代码映射：** 既有 Ghidra 的扁平导入会把资源误认为 ARM 代码；必须重建 ROM/RAM 映射、分段和重定位，再追踪交叉引用。

**安全边界：** 不使用自制刷机包、不把 X-T4 固件刷入 X-S10；在尚无经过验证的恢复路径时，不调用可能修改机身状态的厂商私有 USB 命令。
