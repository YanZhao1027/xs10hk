# Phase 76 — 从原始A32栈字节2到驱动配置类别2，再到+0x828档位函数（2026-10-28）

**核心新证据**：对Fuji **X-S10研究固件3.11/X-T4固件2.12**的原始X6 Section1机器码和只读Ghidra逐条核验，发现Phase75指出的15行数值档位函数`+0x4B0`业务类别不是所有进入驱动初始化分支时都未知。在两机一条明确的接口驱动初始化路径中，原厂代码将六字节参数的**第6字节固定写为2**，使用相同命令上下文基址`0xFFF7B000`把该值写成`+0x4B0`字的**第24–27位类别2**，随后同一驱动函数再构造Phase73–74的`+0x624`命令数据、调用Phase75的数值档位解析器。后者的`case 2`是支持分支，因而**在这个初始化时序、类别未被其它路径覆盖的条件下**，档位函数不会单纯因为该类别不受支持而走`switch default`失败。

**不能由此宣称任何实体X-S10 4K60、HEVC Main10内录或HDMI硬件信号已成功。**原厂ARM静态代码不能证明所有线程和外设的执行时序，更不能证明类别在整个启动过程中一直是2，或当前使用了哪一条时钟/数值档。

## 1. 字节2是由真实ARM栈写入，非反编译器随意推断

| 阶段 | X-S10 v3.11 | X-T4 v2.12 |
|---|---|---|
| 独立驱动入口 | `FUN_0126C388` | `FUN_012425A0` |
| A32准备整数`2`到R3（`mov r3,#2`） | **`0x0126C7F4`** | **`0x01242A0C`** |
| `strb r3,[r11,#-0x4F]`，写六字节参数第6字节 | **`0x0126C7F8`** | **`0x01242A10`** |
| `sub r1,r11,#0x54`，计算六字节参数首址 | **`0x0126C804`** | **`0x01242A1C`** |
| `cpy r0,r5`，传入固定驱动上下文`0xFFF7B000` | `0x0126C808` | `0x01242A20` |
| `BL`六字节命令设置器 | **`0x0126C80C`→`FUN_0126D13C`** | **`0x01242A24`→`FUN_01243354`** |
| 设置器调用处理第6字节的子函数（参数`param_2[5]`） | `0x0126D198`→**`FUN_0126E7A8`** | `0x012433B0`→**`FUN_012449C0`** |
| 写入`+0x4B0`的A32先读后写 | `0x0126E7B0`读、`0x0126E7B8`写 | `0x012449C8`读、`0x012449D0`写 |
| 同一驱动流程之后的Phase73命令构造器 | `0x0126C944`→`FUN_0126D1FC` | `0x01242B5C`→`FUN_01243414` |
| Phase73命令构造器后续的Phase75档位函数BL | `0x0126D298`→**`FUN_0126E804`** | `0x012434B0`→**`FUN_01244A1C`** |

两机上述栈准备的ARM指令、6条直接加载/存储字、4条直接BL目标均由**原始Section1 A32机器字重新核验**，并从Ghidra单独核验栈参数、子调用与xref。将`r11-0x54`作为参数首址，则`r11-0x4F`恰好是其**偏移+5**；`FUN_0126D13C`/`FUN_01243354`读取`param_2[5]`，调用最后一项配置设置器。其它5个字节还控制`+0x4A8`与`+0x4AC`以及`+0x4B0`的另一些位，但它们不是本阶段最终类别码的来源。

## 2. 写入字段与后续开关是同一个地址+同一组位

原厂XS10 `FUN_0126E7A8` / XT4 `FUN_012449C0` 都执行以下等价的只读分析算式：

`context[+0x4B0] = (old_word & 0xF0FFFFFF) | ((byte5 & 0xF) << 24)`

因此来自字节偏移+5的`2`产生**类别字段`0x02000000`**；高四位/低二十四位不被这一设置器覆写。Phase75原厂档位函数从同一`param_1 + 0x4B0`读取并执行等价的`(word & 0x0FFFFFFF) >> 24`类别提取，然后`switch`，其`case 2`是明确的支持值之一（支持类别仍为0、2、3、8、10、12、14）。给定固定参数基址，类别写入的**CPU有效地址为`0xFFF7B4B0`**；其实际映射到何种硬件内存/寄存器并未确立，也完全没有对此地址执行写入。

在具体初始化分支中，类别2设置器出现在`FUN_0126D1FC`构造器之前，后者执行Phase75档位计算。故**“类别未知导致default失败”不应再被描述为该具体初始化路径的必然障碍**。这还不是整个驱动的无条件成功证明：分支本身需要等待接口初始化返回0；调用间仍有其它函数、潜在并发状态，不能排除上下文被重新写入。此阶段没有任何实机消息、HDMI接收器协商结果、物理时钟、sensor/ISP/VPU成功回执。

## 3. 对4K60方向意味着什么（以及不意味着什么）

结合Phase74和75，在这段已看到的原厂初始化路径上可同时识别：

- 输入接口记录→驱动命令`+0x624`位20–21；另一路动态状态→同字的22–23、28–30位。
- 另一份独立六字节配置把第6字节`2`写进命令`+0x4B0`类别位24–27。
- 后续`+0x828`数值档位器对其计算出的任何有效`uint32`具有15行范围表**最后一行`[0,0xFFFFFFFF]`兜底**，并且当前配置的**类别2**属于switch支持项。

这让我们**能够排除两个过度简单的静态失败推断**：①“不在594000等窄时钟范围就必定失败”；②“驱动启动时类别没有合法来源就必定被拒绝”。但即使两个条件都满足，也不意味它们构成真实硬件成功或录制许可；尤其这些数值高度符合**HD/显示接口**语境，无法因此认定是传感器内部4K60或VPU10bit限制器。与独立的Recorder Movie四参数2160P/FPS6查表、实际硬件时序、SPS、持续录制的交点仍**未证实**。
