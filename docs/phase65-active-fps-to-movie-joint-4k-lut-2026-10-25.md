# 第65阶段：补上活动 Recorder FPS → Movie+0x5C6 → 原厂4K联合模式表（2026-10-25）

**核心新证据**：X-S10 固件3.11、X-T4 固件2.12在Movie运行对象初始化期间，都实际调用一份有原厂A32证据的**整块Recorder活动模板→Movie对象复制函数**，而Movie初始化器紧接着以该对象的`+0x5C6/+0x5C7`作多分支视频帧率输入，最后调用96×0x40字节的联合宽高、模式、FPS、变体查表。这**补齐了第64阶段明确标为未知**的“活动Recorder FPS byte `+0x1E`是否进入Movie `+0x5C6`”。第65阶段只证明**静态有条件的配置赋值路径**；期间有其它函数调用、间接指针和模式覆盖可能改变最终值，绝不称作实体X-S10已启用4K60。

## 1. 两机原厂逐指令证实源、目的、长度和调用顺序

| 证据 | X-S10 3.11 | X-T4 2.12 |
|---|---|---|
| Movie初始化器 | `FUN_022D5FEC` | `FUN_022425BC` |
| 活动模板→Movie复制器 | **`FUN_012BD150`** | **`FUN_012957C0`** |
| 活动Recorder配置模板首址 | `0x01C24DD8` | `0x01B83540` |
| 精确复制目的参数 | **Movie指针`+0x5A8`** | **Movie指针`+0x5A8`** |
| 精确复制长度 | **`0x478`=1144B** | **`0x47C`=1148B** |
| 构造参数A32常量 | MOVW/MOVT R5=活动模板，MOVW R2=长度 | 同构，常量各异 |
| MOV R1,R5 / ADD R0,R4,#0x5A0 / ADD R0,R0,#8 | `0x012BD16C/70/74` | `0x012957DC/E0/E4` |
| BL真正通用`memcpy` | **`0x012BD178`→`FUN_012A9148`** | **`0x012957E8`→`FUN_01281848`** |
| Movie初始化器调用复制器的BL | **`0x022D61AC`** | **`0x0224277C`** |
| Movie初始化器在后续调用模式查表的BL | **`0x022D6978`→`FUN_022E123C`** | **`0x02242F48`→`FUN_0224DB10`** |

核心偏移是：

~~~text
源 活动Recorder模板+0x1E (FPS) → 目标 Movie+0x5A8+0x1E = Movie+0x5C6
源 活动Recorder模板+0x1F (相邻字节) → 目标 Movie+0x5A8+0x1F = Movie+0x5C7
~~~

第64阶段已证明第63阶段真实GUI `eMovieFps`字节（GUI+0x6E）在特定GUI→Recorder类型`0x200`消息、转换器和活动模板拷贝条件下成为活动模板`+0x1E`。因此上述第一行接通了**GUI→P→中间Recorder→活动FPS→Movie+0x5C6**的条件式静态路径。第二行也确实随整块拷贝，但**源模板+0x1F的语义和最终内容仍未独立建立**，不得把Movie+0x5C7说成总等于GUI帧率。

原厂Ghidra还确认Movie初始化器先调用`FUN_012BD150(iVar8)` / `FUN_012957C0(iVar8)`，后来读取相同对象`iVar8+0x5C6`、`iVar8+0x5C7`，最后再调用上述联合查表函数。**这不是证明所有实际事件都走到查表，也不排除中间其它调用修改Movie字段。**整块复制后另有针对Movie+0x5B0及+0x5CB的条件规范化，它们不能直接冒充+0x5C6写者。

## 2. 查表真正选哪个FPS字段取决于Movie类别

两机 `FUN_022E123C` / `FUN_0224DB10`的原厂模式矩阵比较（第46阶段已核验完整表及A32）：

- 原厂类别字节来自`*(Movie+0x6018指针 +0x5F5)`。类别**1或2**时，本次查表用`Movie+0x5C7`；**其它类别（包括0）**用`Movie+0x5C6`。
- 这不是仅按GUI帧率决定。还必须同时匹配`u16(Movie+0xADD8)`的模式键以及 X-S10 Movie+`0x9B8` / X-T4 Movie+`0x9BC`的variant。
- 两机完全相同的96条ROM矩阵中，2160P+FPS枚举6的**六条静态候选全部要求类别0**；本阶段已将类0的FPS读取偏移确认为`+0x5C6`，故这六条候选在程序字段上存在与活动Recorder FPS6相接的条件式路径。

在不改动原厂ROM的**离线反事实模式查询**下，令class0、fps枚举6、variant1且其余键合法：

| Mode key高字节 | 模式低字节7的静态查询 | 模式低字节6的静态查询 |
|---|---|---|
| `0x02` | record33 → **3840×2160** | record70 → **1920×1080** |
| `0x07` | record15 → **4096×2160** | record52 → **2048×1080** |

此前Phase47/51已经识别：另一个**运行态4K条件flag**可令模式低字节由7改成6，因此**即使菜单允许FPS6、值经Movie+0x5C6到达，原厂也可能走到1080而不是2160记录**。这些是4键查表的虚拟参数查询结果，**不是相机实机检测结果或任意可执行的解锁指令**。

## 3. 不得过度外推的条件

- Stage63：ROM菜单`MODE_FPS_60`真实允许，但 **菜单准入 ≠ 传感器实际59.94 fps**。
- Stage64：GUI+0x6E到活动模板+0x1E是条件式配置转移，要求GUI→P复制、成功队列传递和模板初始化等事件；不是所有状态都保证。
- 本Stage65：活动模板到Movie+0x5C6是**真实、长度覆盖的整体复制**，却不证明其它中间函数不会改写；类别1/2另走+0x5C7。
- Stage46/47：静态4K59.94模式矩阵有合法候选，但**原厂可能选择1080记录**；VPU/ISP/传感器/SD写入的实机联合准入尚未验证。
- Stage35–36/41–42：VPU位深数字1可通过帧描述符控制流关联到公开MVE ‎0x121 10-bit Y0L2**输入格式**，并确认存在HEVC Encoder固件选择；这**不等于HEVC Main10 SPS输出、真实10bit内录或者实体X-S10 4K60**。

## 4. 可复验的原创成果与安全

`tools/audit_stage65_active_fps_movie_context_joint_lut.py`在第64阶段及其前身原厂SHA/X6审计通过后，逐字核验两机源/目的MOVW/MOVT/ADD/MOV、长度、真实memcpy BL、Movie复制调用BL和联合查表调用BL。只读Ghidra交叉确认同对象复制→读两个FPS字段→表查找顺序，并从原厂第46阶段96×0x40表中独立恢复6条类0/FPS6的2160P记录和两种1080对照；条件假设及未证实运行态结果在结构化JSON中显式False。

`tests/test_audit_stage65_active_fps_movie_context_joint_lut.py`提供**70项不含厂商ROM的纯合成ARM、伪反编译文本及人工ROM矩阵测试**，包括指令寄存器/偏移/分支突变、错误拷贝方向、误将+0x5C7视为+0x5C6、顺序颠倒等负例。
