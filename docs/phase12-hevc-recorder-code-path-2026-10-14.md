# 第十二阶段：X-S10 与 X-T4 的 HEVC 编码控制及录像资源调用链（2026-10-14）

> **本阶段已对 X-S10 3.11 / X-T4 2.12 各前两段解压后的 ARM 程序执行 Ghidra 12.1.4 自动分析，并实证恢复 H.265 编码参数函数、上层编码设置日志、录像任务初始化及缓冲管理的调用关系。**
>
> **重要结论：X-S10 中确有 H.265 编码驱动代码，不仅仅是公共字符串；但两机录像缓冲与状态策略有明确差异，不能简单移植 X-T4 的菜单/模式表来开启 10-bit 或 4K60。是否能实际进行 Main10 机内编码仍未证明。**
>
> 全程**只使用 Ubuntu 本地原厂固件解压副本和 Ghidra，未连接相机、未使用 FF80、未修改固件，也未生成可刷写文件**。

## 1. 固件版本与映射边界

| 项目 | X-S10 | X-T4 |
| --- | --- | --- |
| 离线分析版本 | **3.11** | **2.12** |
| Segment 1 候选基址 | `0x01021000` | `0x01021000` |
| Segment 2 候选基址 | `0x01EAF000` | `0x01E0F000` |
| ARM 入口 Ghidra 实测 | 两段均成功 | 两段均成功 |

上述装载基址已由前一阶段的文件头与入口 ARM 指令验证支持，但**尚未由机身运行态内存验证**。机主实际 X-S10 的普通 PTP 报告固件版本为 **2.10**，不能直接把这里的 3.11 函数地址用于实机操作。

本阶段 Ghidra 对两机 Section 1 和 Section 2 共四个本地项目完成自动分析：`output/ghidra_x6/{xs10_x6s1,xs10_x6s2,xt4_x6s1,xt4_x6s2}`。数据和项目仅在本地 `output/`。

## 2. 录像资源表：两机 126 个名字及数字 ID 完全相同

新增工具 `tools/compare_video_resources.py` 在两机 Segment 2 内识别 `UI_MOVIE_MODE_*` 名称字符串，再用已恢复的装载基址验证指向名称的 32 位绝对指针，读取随后的资源 ID。

| 指标 | X-S10 3.11 | X-T4 2.12 |
| --- | ---: | ---: |
| `UI_MOVIE_MODE_*` 名称个数 | **126** | **126** |
| 各名称及数字 ID | **126/126 全部与 X-T4 相同** | **126/126 全部与 X-S10 相同** |
| 包含 `4K_59_94P` 的名称 | **8** | **8** |
| 包含 `4K_50_00P` 的名称 | **8** | **8** |
| `UI_MOVIE_CODEC_H265` ID | **0** | **0** |
| `UI_MOVIE_CODEC_H264` ID | **1** | **1** |
| `UI_MOVIE_MOV_H265` ID | **0** | **0** |
| `UI_MOVIE_MP4_H265` ID | **2** | **2** |

具体例子：`UI_MOVIE_MODE_4K_59_94P_400M_16_9` 在 X-S10 Segment 2 的文件偏移为 `0x006E8AA0`，表项位于 `0x006D3594`，ID `0`；X-T4 的对应文件偏移 `0x006E69A0`，表项位于 `0x006D22F8`，ID 也为 `0`。这两个字符串及表项都是**对应解压文件内的偏移**。

**解释：** 这是共用的“资源名称→ID”查找表，不是经过证实的可用录像模式表。它能证明 X-S10 编入了 4K59.94/50 的命名资源，**不能证明传感器读出、记录任务、VPU 编码器和存储带宽允许以此模式运行**。

### 文件格式菜单的不同

在 Segment 1 中按独立的 NUL 分隔字符串比较，H.264/H.265 的 `MSG_*FILEFORMAT*` 名称存在清晰差异：

X-T4 独有：

- `MSG_VALS_TITLE_FILEFORMAT_MOVH265`
- `MSG_ITEM_TITLE_FILEFORMAT_MOVH265`
- `MSG_COMMENT_FILEFORMAT_MOVH265`
- `MSG_COMMENT_FILEFORMAT_MOVH264`
- `MSG_COMMENT_FILEFORMAT_MP4H264`

X-S10 独有：

- `MSG_COMMENT_FILEFORMAT_MOVH264IIII2`
- `MSG_COMMENT_FILEFORMAT_MP4H264IIII2`

这支持两机**电影文件格式 UI/消息资源存在差异**，但不能直接定位真正的功能许可分支。

## 3. 实际上层编码枚举：注意它和 UI ID 不是一回事

Ghidra 在 Segment 1 发现以下对应函数：

| 功能 | X-S10 3.11 | X-T4 2.12 |
| --- | --- | --- |
| 编码枚举→诊断名称 | `FUN_01034DC4` | `FUN_01035078` |
| 记录 `eModeMovieCodec` 更改 | `FUN_0115B578` | `FUN_0112FD80` |
| 读取/更新编码设置的上游函数 | `FUN_01179DC0` | `FUN_0114DAB4` |
| 上游函数访问的编码配置项目 ID | `0x3FC` | `0x3E5` |

两台固件中，**编码枚举→诊断名称**的反编译逻辑一致：

- 运行时编码枚举 `0` → `MODE_MOVIE_CODEC_H264`
- 运行时编码枚举 `1` → `MODE_MOVIE_CODEC_H265`
- 运行时编码枚举 `2` → `MODE_MOVIE_CODEC_NUM`
- 其他值 → 空

Ghidra 交叉引用显示，这些枚举映射函数是在记录输入模式从 A 变 B 的调试事件中调用的，**不是我们已经确认的编码器启动选择器**。

**关键警告：UI 资源表里的 H.265 ID=0，与运行时 `eModeMovieCodec` 枚举的 H.265=1 属于不同的编号语境。** 不能把它们混淆、据此盲改数值或刷机。

交叉引用结果：

- X-S10 `FUN_01034DC4` 调用点 `0x0115B5DC`、`0x0115B5E8`，均在 `FUN_0115B578`；
- X-T4 `FUN_01035078` 调用点 `0x0112FDE4`、`0x0112FDF0`，均在 `FUN_0112FD80`；
- X-S10 `FUN_0115B578` 当前识别到一处调用 `0x01179E54`；
- X-T4 `FUN_0112FD80` 当前识别到 `0x0114DB48` 和 `0x0115B314` 两处调用。

X-T4 后一处位于一组录像设置重建/恢复流程 `FUN_0115B234`，而 X-S10 目前没有找到与其直接对应的**同一处调用**。这可能反映程序流程差异，也可能与优化、函数重排及 Ghidra 未识别的引用有关，**不能把“当前发现的调用数”当成已证实的功能关闭位**。

## 4. H.265 编码参数驱动：两机均有真实、结构相似的实现

这是目前最重要的正面结果：Ghidra 直接找到引用 `h265_drv_set_enc_param` 诊断信息的**实际 ARM 编码参数处理函数**。

| 实际驱动功能 | X-S10 3.11 | X-T4 2.12 |
| --- | --- | --- |
| 编码参数处理函数 | `FUN_011F9B84` | `FUN_011CD230` |
| 反汇编函数长度 | **368 字节** | **368 字节** |
| 编码参数函数的一处直接调用 | `0x011F7464` | `0x011CAB10` |
| 简短封装函数 | `FUN_011F745C` | `FUN_011CAB08` |

两份独立反编译结果有同样的行为框架：

1. 检查 H.265 设备工作模式是否可接受；不满足时报告错误。
2. 检查/更新编码序列状态。
3. 检查回调参数非零，保存回调函数参数。
4. **逐项将 15 个 32 位字（60 字节）编码参数**复制到驱动的全局参数结构。
5. 标记调度事件并向 VPU/驱动线程发起事件/等待；通过返回码报告成功或错误。

存在相似的日志，例如编码参数检查失败、设置参数成功、调度事件、事件返回等。两台相机都包含这个**可执行处理路径**，因此不能再说 X-S10 仅保留了 H.265 文字而没有驱动代码。

**但是：** 这仍然**不是**证明 X-S10 录制任务会实际选用 H.265，更没有确认这 60 字节里的哪一字段对应 Main10/profile/chroma 或者具体位深。简短封装函数在当前 Ghidra 的直接调用图中没有识别到上游静态调用；可能由间接调度/API 表或未恢复的结构引用，不能把“没有引用”当成代码完全不可达。

## 5. 录像任务的真实差异：缓冲/等待策略不能直接移植

第二段程序中的实际录像初始化函数和相关引用已经恢复。以下为有直接调用的函数（非孤立常量）：

| 功能 | X-S10 3.11 | X-T4 2.12 |
| --- | --- | --- |
| 录像模式更新 | `FUN_022D1BC8` | `FUN_0223E158` |
| 记录帧等待/有效 YC 数量相关函数 | `FUN_022D3D30` | `FUN_022402F8` |
| 录像上下文初始化 | `FUN_022D3E00` | `FUN_022403C8` |
| 初始化入口/事件分派 | `FUN_022E6BA0` | `FUN_02253478` |
| 时间码帧率相关映射 | `FUN_022D2320` | `FUN_0223E8EC` |

### 最可复现的分支差异

在“有效 YC 数量/录像帧等待”相关函数中，**同一状态变量**进入下列不同分支：

| 状态枚举 | X-S10 3.11 的基准值或路径 | X-T4 2.12 的基准值 |
| --- | --- | --- |
| 1、4、5 | 6 | 11 |
| 2、6 | 7 | 11 |
| 3 | 特殊路径，最终等待量按 0 处理 | 14 |
| 7 | 特殊路径，最终等待量按 0 处理 | 13 |

两机处理的其他步骤基本相似：读取活动 YC 数量，计算其与基准值的差，并写入帧等待计数；超出范围时报告诊断消息。

**不能把这些基准值直接解释成“8-bit/10-bit”“帧率上限”或“硬件编码通道数”**：该状态枚举的实际语义和数据单位尚未恢复。但它已经充分证明了录像运行策略存在机型依赖。

### 录像上下文结构步长

录像上下文初始化中，X-S10 使用 **`0x3C318`（246,552 字节）**作为上下文索引步长，X-T4 使用 **`0x4B0A0`（307,360 字节）**。

两处都用于按录像上下文序号寻址一批字段，其余总体的处理结构相似。X-T4 的步长大约比 X-S10 大 25%。这可能反映缓冲布局或结构包含的数据不同；**绝不能假定把 X-T4 的函数或常量直接移植到 X-S10 就会安全**。

两个初始化函数都由更大的录像状态/事件处理函数调用；已识别到直接 BL 指令，因此不是仅靠字符串猜测的孤立代码。

### 共同部分

录像模式更新函数两机各为 100 字节，均按照一组 1/2 类型执行不同处理分支；时间码帧率辅助函数两机各为 92 字节，按输入状态返回 24/25/30 等数字。**这些值不等于 4K60 可用性的保证。**

## 7. 复现与代码

本轮新增：

- `tools/compare_video_resources.py`：解压后的 UI 资源/数值 ID 对照（支持两机注册表及 H.265 菜单差异）。
- `tests/test_compare_video_resources.py`：所有数据均为人造合成输入。
- `ghidra_scripts/ProbeX6Refs.java`：通过加载后的 ARM 虚拟地址获取代码和数据交叉引用。
- `ghidra_scripts/TraceX6Function.java`：定位包含目标地址的 ARM 函数、输出附近指令和限制长度的反编译结果。

在 Ubuntu 上：

~~~bash
cd /home/zyubuntu/xs10hk
python3 tools/compare_video_resources.py \
  --xs10-dir output/x6-xs10 \
  --xt4-dir output/x6-xt4
python3 -m unittest discover -s tests -q
~~~

仅输出资源**标签和 ID**，不上传二进制和设备信息。

已在本地 Ghidra 项目对两机各自自动分析 Section 1 + Section 2，并通过脚本追踪。举例：如想复核 X-S10 H.265 驱动：

~~~bash
/home/zyubuntu/tools/ghidra_12.1.4_PUBLIC/support/analyzeHeadless \
  output/ghidra_x6 xs10_x6s1 \
  -process section-1.bin -noanalysis \
  -scriptPath ghidra_scripts \
  -postScript TraceX6Function.java 011f9b84 \
  -postScript ProbeX6Refs.java 011f9b84
~~~

当前测试数 **75 项，全部通过**，Ubuntu Git 工作区干净。

## 8. 下一步精确研究路线

1. 从 X-T4 已有 Main10 内录出发，**逆向其上层选择 H.265 → 传入编码参数的完整调用链**，找出 15 个 32 位参数中的 codec profile/bitdepth 字段；再比对 X-S10。
2. 从 `FUN_022D3D30` / `FUN_022402F8` 出发，追踪驱动输入状态和“活动 YC 数量”数据源，判断 buffer/wait 差异是否和传感器时序、编码位深或写卡吞吐有关。
3. 在 X-T4 中寻找真正的**可用模式筛选/菜单生成**逻辑，区别它与共用的 126 项名称注册表；对应检查 X-S10 是否有显式机型/硬件能力掩码。
4. 分析 RAW/HDMI 输出位深配置与**内部 VPU 编码入口**是否汇合；外接录机的 10-bit 不能替代 Main10 证据。
5. 即使得出可修改的代码点，也只能先在 Ubuntu 做**离线模拟与补丁产物验证**。本机 X-S10 2.10 地址与离线 3.11 不符，上次 FF80 RAM 访问曾让相机无法正常关机；在完整固件封装与独立救砖方案出现前，**不再次读取实机 RAM，也不刷入任何修改包**。

本阶段没有找到被证明可安全修改的“10-bit/4K60 一键开关”。最值得继续投入的是**已有可执行 H.265 编码驱动的上层参数来源**，以及已证实存在差异的录像缓冲策略。
