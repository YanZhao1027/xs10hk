# 第十五阶段：恢复 96×64 字节真实录像参数查表，确认 X-S10 与 X-T4 的 4K60 候选记录完全相同（2026-10-14）

> **最重要的新发现**：已通过三机联合 Ghidra 工作继续向上恢复 X-T4 / X-S10 的录像参数构建路径，直接从读取实际 ARM 代码的 420 字节查表函数入手，恢复每条 64 字节记录的匹配键及它们用于生成的视频宽高。**X-T4 2.12 与 X-S10 3.11 的录像参数查找表恰好各有 96 条记录；6,144 字节零差异，4K（4096/3840×2160）与 59.94 fps 的组合两机均各存在六条记录。**
>
> **重要限定**：这是参数生成的**候选表**，不是已证明的“该机可用模式列表”。正常 UI 是否会传递这些键、VPU 会否接受 Main10、传感器能否 4K60 读出、文件混流及写卡能否持续运行，都尚未验证。**没有发现可安全刷写的补丁点**。机主实机 2.10 与离线 X-S10 3.11 地址不相容。
>
> **全程只分析用户授权 Ubuntu 上离线的原厂固件与本地 Ghidra 项目；未操作 FF80、USB、相机 RAM、SD 卡或闪存。**

## 1. X-T4 和 X-S10 相同的实际数据查表函数

第十四阶段已恢复三机录像任务构建 HEVC 参数时的 ARM 直接调用（详见[第十四阶段](phase14-cross-segment-hevc-params-2026-10-14.md)）。沿着录像初始化所读取的上游模式结构（存放为 0x600/0x602/0x608/0x60E/0x60F 附近的字段）反向追踪，找到 X-T4/X-S10 分别包含一个 **420 字节 ARM 函数**：

| 对象 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- |
| 录像参数查表函数 | **\`FUN_0224DB10\`** | **\`FUN_022E123C\`** |
| 420B 函数实际 LUT 虚拟地址 | **\`0x026FDE5C\`** | **\`0x027A0DBC\`** |
| 候选 Section 2 装载基址 | \`0x01E0F000\` | \`0x01EAF000\` |
| LUT 在解压后的 Section 2 中的文件偏移 | \`0x008EEE5C\` | \`0x008F1DBC\` |
| 记录长度 | **64 字节** | **64 字节** |
| 有效记录数量 | **96** | **96** |
| 结束标记（第 97 条首字节） | \`0xFF\` | \`0xFF\` |
| **96 条有效记录合计** | **6,144 字节** | **6,144 字节** |
| SHA-256 | \`43852b4bb7454ad54b1a9d018432250829abb334dec9961fb54e4862407199bc\` | **完全相同** |

注意：上表的 0x02... 都是用于离线 Ghidra 的**候选虚拟装载地址**，本节只利用原厂解压内容核验；X-S10 实机运行的版本并非 3.11，绝不能直接使用它们操作机身。

### ARM 代码如何使用 64 字节记录

两机查表函数按照相同的四项键扫描 LUT，每次移动指针 **\`+0x40\`**，在记录首字节 \`0xFF\` 时终止：

| 记录偏移 | 功能 | 与哪类运行状态匹配 |
| --- | --- | --- |
| \`+0x00\` | 8-bit 编号 | 录像上下文配置 \`+0x5F5\` |
| \`+0x01…+0x02\` | LE \`uint16\`，两个尺寸子编码 | 录像上下文 \`+0xADD8\` |
| \`+0x03\` | 帧率编号（1…6） | 当前标准/高帧率设置 \`+0x5C6/+0x5C7\` |
| \`+0x04\` | 另一个模式/裁切限定值（0…3） | 上层上下文的相应字段 |
| \`+0x06\` | 16-bit 附加数值 | 生成配置 \`+0x604\` |
| \`+0x08\` 起的多项 DWORD | 编码参数的配置索引和对应值 | 生成码率、格式相关字段 |
| \`+0x14,+0x18,+0x1C,+0x20\` | 动态配置数据索引 | 生成上下文 \`+0x60E/+0x60F\`，其语义**未确认** |
| \`+0x24\` | 单字节模式字段 | 生成 \`+0x610\` |

**不能因为某个字段最终得到 \`8\` 就把它直接解释成 “8-bit codec”。** 这些字段位于不同层次的运行时初始化结构，可能有缓冲格式、通道号、尺寸对齐等其它意义；还没有解出选项码定义。

## 2. 已经从可执行 lookup 函数真正恢复 4K/FHD 像素尺寸

表的 \`record[1]\`、\`record[2]\` 传入两机对应的两个 **88 字节 ARM 宽/高查表函数**。不是根据 \`4K\` 菜单名称去猜宽高：

| 参数 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- |
| 宽度转换函数 | \`FUN_012A2F90\` | \`FUN_012C9354\` |
| 高度转换函数 | \`FUN_012A3058\` | \`FUN_012C941C\` |
| 宽度查找数组首地址 | \`0x0168BAE4\` | \`0x0171BF0C\` |
| 高度查找数组首地址 | \`0x0168BDC8\` | \`0x0171C1F0\` |

两个函数都按**5 列 DWORD 数组**检索，行号为 \`record[1]\`，列号为 \`min(record[2],4)\`。按原厂固件真实表项求值得到：

| 记录 \`+0x01…+0x02\` | 宽度（像素） | 高度（像素） | X-T4 与 X-S10 是否相同 |
| --- | ---: | ---: | --- |
| \`0x0707\` | **4096** | **2160** | 是 |
| \`0x0207\` | **3840** | **2160** | 是 |
| \`0x0706\` | 2048 | 1080 | 是 |
| \`0x0206\` | 1920 | 1080 | 是 |

这两个尺寸转换函数的实际结果随后被写入录像初始化结构。**因此，这是可执行的数据路径证据，而不是偶然重合的字符串。**

## 3. 4K × 59.94 fps 的模式组合究竟有多少条

根据第十四阶段验证的录像 HEVC 参数 \`input[2]\`，帧率键 \`record[3]\` 取值 1…6，对应约 23.98、24、25、29.97、50、59.94 fps。将此与上面的真实宽高映射组合：

| 录像尺寸 | X-T4 LUT 总记录 | X-S10 LUT 总记录 | 其中每机 59.94 fps 的记录 |
| --- | ---: | ---: | ---: |
| 4096 × 2160 | 18 | 18 | **3** |
| 3840 × 2160 | 18 | 18 | **3** |
| 2048 × 1080 | 18 | 18 | 3 |
| 1920 × 1080 | 42 | 42 | 7 |
| **合计** | **96** | **96** | **16** |

每台机身对 6 种 fps 编号都**恰好包含 16 条候选记录**。所以任一机身都包含：

- **3 条** 4096×2160/59.94 的低层参数匹配；
- **3 条** 3840×2160/59.94 的低层参数匹配；
- 合计 **6 条** 真正的 4K/59.94 fps 候选条目。

并且**这 96 条记录在 X-T4 2.12 与 X-S10 3.11 中完全相同**，SHA256 一致，0 字节差异。可重复解码与单元测试见下一节。

**关键解释：** 这比“固件里有 4K60 名称”强很多。但 LUT 不是相机的“支持范围白名单”。比如 X-S10 官方没有 4K60 录制，尽管有相同表项，这恰恰证明真正的使用许可或物理资源校验**一定存在于这张参数表之外，或者输入选择永远不会到达这些记录**。这些不是可直接打开的 UI 菜单条目。

## 4. 排除误判：“强制 8”的代码两台机身都有

扫描 X-S10 中写入上下文 \`+0x60E/+0x60F\` 的 ARM 指令时，发现 \`FUN_02235ABC\` 暂时把两个字段都设为 **8**，用于特殊录像/4K 参数修正，然后恢复先前状态。

**不能把它当成 X-S10 的独有 8-bit 锁。** 使用与调试日志 \`recfCalcCorrect4kParam\` 的交叉引用，找到 X-T4 中**同样为 1,056 字节、几乎逐句对应的**修正函数：

| 对照 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- |
| 4K 参数修正函数 | **\`FUN_021A27C8\`** | **\`FUN_02235ABC\`** |
| 函数大小 | **1,056 B** | **1,056 B** |
| 模式分支临时使用 \`8\` | 存在 | 存在 |
| 所修正的上下文字节偏移 | \`+0x611/+0x612\` | \`+0x60E/+0x60F\` |
| 调试字符串 | \`recfCalcCorrect4kParam\` | \`recfCalcCorrect4kParam\` |

这是一条很有用的**排除结果**：看似直接的“X-S10 设置 8”并非 Main10 被禁用的特异性证据，盲改将极其危险。

## 5. 后续潜在分歧：动态资源/配置区初始化，而非共同的 96 条表

既然原始 LUT 完全相同，却无法确认 X-S10 实机获得相同录像能力，就要继续向 LUT 索引最终返回的 **动态配置值** 追踪。

两机用于读取 LUT 选项值的 32 字节 ARM 函数，在返回时会从一片动态初始化的内存区域读取单字节：

| 行为 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- |
| 从配置空间读取一个 byte | \`FUN_01263954\` | \`FUN_0128DFA8\` |
| 所用配置空间基址指针变量 | \`0x017B2764\` | \`0x01843554\` |
| 相应初始化函数 | **\`FUN_01263F40\`** | **\`FUN_0128E594\`** |
| 初始化所写目标基址 | **\`0x045E8000\`** | **\`0x045E8000\`** |

两个初始化函数结构相似，都配置动态内存区、尝试从映射源（含地址 \`0x07500000\`）拷贝/恢复数据，并写入多项设备/平台相关配置键。

但观察到**有差异**：

| 初始化字面配置 | X-T4 | X-S10 |
| --- | --- | --- |
| 一处清零/重建长度 | \`0x4C0000\` | \`0x480000\` |
| \`set(config_key=0x204, value)\` | \`2\` | \`1\` |
| \`set(config_key=0x205, value)\` | \`0x16\` | \`0x90\` |
| \`0x4069/0x406A/0x406B/... \` | 相同 | 相同 |

**这里的 \`0x204\`、\`0x205\` 与内存重建长度目前只属于“机型配置差异”的静态证据。** 它们也可能对应 SD 卡槽数量、内存区域、板级配置或其它硬件属性；不能推测成 Main10 能力开关。尤其 X-T4 有双 SD 卡槽而 X-S10 单槽，这可能造成某些非编解码器因素差异；**尚未证明实际编码值的因果关系**。

由于配置在运行时被初始化、可能来自独立映射区域，**不能把两机公共 LUT 的“同一个索引”误认为两机运行时返回一定相同的字节**。这可能是接下来的研究重点。过去对 X-S10 使用 FF80 读取 RAM 已造成冻结/关机异常，本阶段**不恢复这条风险路线**。

## 7. 下一步的严格检验标准

为了真正判断“X-S10 的 10-bit 内录、4K60 是否可解锁”，必须继续：

1. 追踪 **UI/模式许可到 LUT 四字段输入键的产生过程**，确认 4K59.94 组合在 X-T3/X-T4 的有效调用路径上可达、在 X-S10 哪一步不再可达。
2. 解析运行时动态配置映射到 LUT 的 \`+0x14/+0x18/+0x1C/+0x20\` 的实际返回值，并结合 X-T3 / X-T4 已知 Main10 内录恢复 profile/bitdepth 的语义。尤其要分清码率、像素排列与编码 Profile；**不能把未知值 \`1\`、\`3\`、\`8\` 当成 Main10 开关**。
3. 若发现合法参数路径存在而 UI 隐藏，也仍需证实 X-S10 实际 4K60 传感器/ISP/VPU/热预算，并另外解决重封装、校验/签名、同版本地址及**独立救砖路径**。

**结论更新：真实下层视频查找表不是 X-S10 4K60 缺失的解释，因为它与 4K60 正对照 X-T4 完全一致。应继续查找表之前的模式许可与表之后的动态参数/硬件检查。**
