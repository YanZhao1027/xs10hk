# 第十阶段：X6 离线装载边界与 X-S10 恢复路径核查（2026-10-14）

> 本阶段仅访问**Ubuntu 本地的原厂固件副本**与公开技术文档，**没有连接或向机身发送任何诊断指令**。X-S10 已曾因读取未知 RAM 地址而卡死，最终在打开电池仓、拔下电池并重新装入后恢复正常开机。**此前的 FF80 RAM 试验继续禁用。**

## 摘要：获得了什么

1. **强化确认两套固件各四处压缩段的精确文件边界**。按 `header_file_offset + 20 + packed_size` 得到候选终点；从终点到下一个 `0x20000` 对齐边界，**8/8 段全部为 `0x00` 填充**。这支持 `packed_size`、20 字节候选头以及分段对齐的结构解释。
2. 全部 8 处头字段均含 `0x4000`（16 KiB）和 `4`；这与 [fffw 作者关于芯片硬件解压器按 16 KiB 区块经 DMA 工作的说明](https://github-wiki-see.page/m/tiredboffin/fffw/wiki/Route-0xff80) 相符。**相关性不是完整结构定义或解压成功**。
3. 对 X-S10 3.11 和 X-T4 2.12 原厂 DAT 的多种常见校验假设做了完整文件实测，包括原字节总和、逐字节取反后的总和、其负值、32 位小端字求和、CRC32，**都不能直接复现各自头部的 checksum 字段**。**尚未建立 X6 的完整校验或签名验证方法**。
4. 查明官方“恢复更新失败”指南仅确认**某些更新失败状态**能重新从 SD 读取升级文件，另一些情况仍必须交授权维修站；既没有确认 X-S10 一定存在独立于受损主固件的 BootROM 恢复链，也没有证实任何 X-S10 自制固件救砖方案。
5. `ffun` 确实能按作者说明生成 DAT 的解压后 ELF 与地址清单，但核心硬件 LZ 解压工具在其公开库中仍不完整（`fflz` 源码未发布）；不能假装已恢复 X-S10 程序映射。

## 公开校验算法的适用性疑问

参考 [FujiHack firmware header 文档](https://wiki.fujihack.org/firmware/) 和其 [patcher.js 的增量修改逻辑](https://github.com/fujihack/patcher/blob/master/patcher.js)：其代码会按**取反后的原始代码字节差值**调整 DAT 头部的 checksum 值。不过，这不等价于证明“对完整 X6 payload 求一次简单总和即为头部 checksum”。

实际 X-S10：
- 头部字段 `0x63e97e8f`
- 原 DAT payload 字节总和（模 `2**32`）：`0x60a19051`
- 取反 payload 字节总和：`0xa7c31f8f`
- 原 payload CRC32：`0x90d0d811`

实际 X-T4：
- 头部字段 `0x56831a6c`
- 原 DAT payload 字节总和：`0x538616a7`
- 取反 payload 字节总和：`0xb7db2da5`
- 原 payload CRC32：`0x6ef4c032`

此外还计算了 32 位求和、取反求和和相应 CRC32，亦均不相符；详情见程序输出。

**不可据此断定 checksum 字段是假值**。可能涉及不同的校验覆盖区、多个子块、预置常数、修正字段或旧工具的版本适用差异。**在能从原厂两个样本独立复算得到头部数值之前，不得制作“可刷写”修改固件。**校验符合也仍然不能证明存在或不存在额外的密码学签名、版本/机型判断。

## 官方恢复证据及边界

1. [富士 X-S10 官方 3.11 下载与升级说明](https://www.fujifilm-x.com/en-us/support/download/firmware/cameras/x-s10/) 明确要求使用充满电的电池，强调更新中断可能造成相机无法正常工作。
2. [富士官方升级错误与恢复提示](https://fujifilm-dsc.com/en-int/manual/error_message_recovery/) 中，“恢复时找不到 SD 固件”的场景建议放入 SD 卡并重启；**另一些恢复失败场景直接要求授权维修站处理**。它不能保证 X-S10 在任意主固件/启动分区损坏时仍能启动恢复程序。
3. [X-S10 官方固件版本检查说明](https://fujifilm-dsc.com/en-int/manual/x-s10/technical_notes/firmware_version/) 记录了正常可开机状态下按住 DISP/BACK 启动进行固件版本检查。**不能把正常固件版本界面等同于受损固件也能运行的独立 BootROM 救援入口**。
4. [fffw 项目说明](https://github.com/tiredboffin/fffw) 把 `ffre`（基于 SD 的救砖方案）标为未公开、已暂缓，仅在 **X-E2** 上进行了部分测试。**没有 X-S10 适用性证据**。

因此：官方维修是目前最可靠的失败后备路径，**不能宣称已经找到了实证有效的 X-S10 DIY 救砖方法**。

## 复现程序

本次新增脚本 `tools/package_invariants.py` 仅做文件结构和候选校验的读取：

```bash
cd /home/zyubuntu/xs10hk
python3 tools/package_invariants.py /home/zyubuntu/Downloads/FWUP0025.DAT
python3 tools/package_invariants.py /home/zyubuntu/Downloads/FWUP0024.DAT
python3 -m unittest discover -s tests -q
```

仅处理本地官方文件，不向相机发 USB/PTP/FF80 指令，不生成修改后 DAT，不上传固件到 GitHub。**全项目 47 项离线测试通过。**

## 后续最有价值的方向

1. 深入提取各候选头之后的**16 KiB 逻辑块索引和压缩控制字**，利用两机相同区段比对，逐步验证硬件 LZ 流格式；这条路线不需要操作相机。
2. 优先解析 X6 启动区中对压缩块源地址、DMA 目标地址的设置，以建立可信文件偏移 → 运行时内存地址的映射；不能把文件位置误作虚拟地址。
3. 核对原厂更新包的 checksum 覆盖区和验证函数；对每个原厂样本必须能复算一致。之后再研究其它版本/型号限制与潜在签名。
4. 联系具有 X-S10 / X-Processor 4 经验的固件研究者，请其确认有无只读地址映射资料和经实机验证的救砖工具；没有可验证文档前**不在用户这台 X-S10 上重试 FF80 RAM 读取或自行刷写**。

本阶段已经得到可靠的压缩段文件范围及明确的恢复边界，但还**没有**得到主程序运行地址、可用 H.265 Main10 初始化代码，或保证成功的固件刷写/救援程序。
