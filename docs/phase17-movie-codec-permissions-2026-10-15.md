# 第十七阶段：破解 X-S10/X-T4 的 H.265 设置权限矩阵——两机均允许 1（2026-10-15）

> **本阶段最重要的静态证据：我们不仅看见了名为 H.265 的字符串及其驱动，而且找到了实际处理用户设置的“允许值检查函数”，从相机解压固件中还原类别列表、配置项索引表以及每个候选数值的权限字节，并且**：
>
> - **X-T4 2.12 的录像类别 0x2D、eModeMovieCodec=1（H.265）在通用设置验证中得到允许；**
> - **X-S10 3.11 的录像类别 0x2D、eModeMovieCodec=1（H.265）在完全对应的通用设置验证中**同样**得到允许。**
>
> 两机都是 **H.264(0)→标志2、H.265(1)→标志1**；通用合法性检查接受 1–4、拒绝 0，默认取值/回退检查倾向 2 或 4。**X-S10 这一层没有简单的“H.265 被禁止”开关。**
>
> **但：它不是 H.265 Main10 成功初始化证明。** 录像菜单是否暴露、上游许可是否投递 H.265、底层 VPU profile/bitdepth 是否允许、容器能否写文件均仍未验证。没有找到安全的 patch 位置，更没有刷机。

## 1. 先从可执行代码确定枚举值，而不是根据菜单 ID 猜

两机均在**实际 76 字节 ARM 枚举名称函数**中确定：

| 机型 | 函数 | 入参 0 | 入参 1 |
| --- | --- | --- | --- |
| X-T4 | \`FUN_01035078\` | \`MODE_MOVIE_CODEC_H264\` | \`MODE_MOVIE_CODEC_H265\` |
| X-S10 | \`FUN_01034DC4\` | \`MODE_MOVIE_CODEC_H264\` | \`MODE_MOVIE_CODEC_H265\` |

这确认运行时**\`eModeMovieCodec\` 编码枚举**中：**0=H.264、1=H.265**。它与 \`UI_MOVIE_CODEC_H265\` 的 UI 资源编号不是同一数值体系。

实际记录/更新编码枚举的程序（两机分别为 148 字节）：

- X-T4 \`FUN_0112FD80\`；
- X-S10 \`FUN_0115B578\`。

它们接受参数数值，更新 \`eModeMovieCodec\` 的全局状态并在满足条件时记录 \`_INPUT_eModeMovieCodec_\` 调试信息。两机行为对应。**没有在这些单纯 setter 中发现硬编码强制 H.264 的语句**，但合法模式许可也不完全由这些 setter 决定。

## 2. 录像设置初始化确实调用了“三参数设置合法性验证”

两机的录像/设置值装载函数：

| 对象 | X-T4 | X-S10 |
| --- | --- | --- |
| 设置恢复/加载函数 | \`FUN_0114DAB4\` | \`FUN_01179DC0\` |
| codec 设置项 ID | \`0x3E5\` | \`0x3FC\` |
| 已验证的设置类别 | \`0x2D\` | \`0x2D\` |
| settings validator 入口（16 字节跳板） | \`FUN_01025504\` | \`FUN_010253A4\` |
| settings validator 真正实现 | **\`FUN_011222DC\`** | **\`FUN_0114DFAC\`** |
| 默认/回退值查找入口（16 字节跳板） | \`FUN_01025514\` | \`FUN_010253B4\` |
| 默认/回退查找真正实现 | \`FUN_011224C8\` | \`FUN_0114E198\` |

例如 X-S10 初始化代码最终调用等价于：

~~~c
candidate = convert_setting(0x3FC, stored_value, ...);
if (!is_valid_setting(/*category*/ 0x2D, /*codec item*/ 0x3FC, candidate)) {
    candidate = fallback_setting(/*category*/ 0x2D, 0x3FC);
}
set_runtime_eModeMovieCodec(candidate);
~~~

X-T4 用对应的 \`0x3E5\` 代替 \`0x3FC\`，设置类别仍为 \`0x2D\`。

**这不是 UI 字符串推导**；上述函数经 Ghidra ARM 反编译及直接 \`BL\` 交叉验证，能执行真正的按候选值检查。所以上一个阶段“需要找到实际上层限制”的目标，已经进入了确切的内存表和判断式。

## 3. 允许值矩阵格式已解

\`FUN_011222DC\` 和 \`FUN_0114DFAC\` 先通过已编译的类别列表获取当前 \`category_index\`，再按设置 ID 扫描 \`(uint32 setting_id, uint32 option_array_pointer)\` 的 8 字节索引列表，找到选项数组。

一个数组的每条记录为：

~~~text
uint32 option_numeric_value
byte   permission_flag_for_category_0
byte   permission_flag_for_category_1
...
byte   permission_flag_for_category_n
padding to 4-byte alignment
~~~

遇到 \`0x7FFFFFFE\` DWORD sentinel 停止查找。

核心验证判断（精确符合 ARM 反编译语义）为：

~~~c
return (uint8_t)(permission_flag - 1) < 4;
~~~

即权限标志 \`1、2、3、4\` 均**通过该通用合法性测试**，0 不通过。另一条“获取默认/回退值”的函数优先寻找权限标志 **2 或 4**，而不是 1（这是选项 flag=2 更类似默认项的独立代码证据）。

| 字段 | X-T4 2.12 | X-S10 3.11 |
| --- | --- | --- |
| category 字节数组起点 | \`0x014090A0\` | \`0x0141AE54\` |
| category 条目数 | **9** | **24** |
| 录像 category ID | \`0x2D\` | \`0x2D\` |
| \`0x2D\` 在 category 数组中的索引 | 8 | **23** |
| 8 字节 \`(ID,ptr)\` 索引起点 | \`0x014090AC\` | \`0x0141AE70\` |
| 有效顶层配置项索引数 | 254 | 252 |
| H.265 codec 配置项 ID | \`0x3E5\` | \`0x3FC\` |
| 对应选项数组首地址 | **\`0x0140D344\`** | **\`0x01421C80\`** |
| 每个选项记录的字节步长 | **16** | **28** |
| H.265 选项条目数量 | 2（0、1） | 2（0、1） |

类别数组均以 byte \`0x2E\` 结束；索引数组以空指针结束。表地址均是**对应固件在 Ghidra 里的候选虚拟装载地址**，不能当成实机 2.10 内存地址。类目数不同解释了为何 X-S10 的单条权限记录显著更长：多出的 15 个类别需要额外的权限位，并不必然是编解码能力差异。

## 4. 在真实二进制逐字节解出的 H.265 权限结果

对官方固件解压 Section 1 读取这两张选项表，分别解读 16 字节 / 28 字节结构，验证每个 option 的 category 0x2D 标志：

| 类别 \`0x2D\` 的 eModeMovieCodec | X-T4 2.12 | X-S10 3.11 | 核心 validator 结果 |
| --- | --- | --- | --- |
| **0 = H.264** | flag **2** | flag **2** | 两机均通过，且是优先默认/回退项 |
| **1 = H.265** | flag **1** | flag **1** | **两机均通过，但都不是默认项** |

对**其他类别**，两机 H.265(1) 的 permission_flag **全部为 0**；它只在录像相关的 \`0x2D\` 类别中开放。这强化了我们不是错误地分析到不相干设置项；它的允许范围与 eModeMovieCodec 的语义高度一致。

尤其重要：X-S10 表并非没有 \`H.265=1\` 的权限。**两机的通用合法性测试在对应类别会返回相同逻辑结果**，因此“X-S10 禁止 HEVC 的原因，就是这张设置选项表不允许数值 1”的简单假说已经被排除。

**这与官方 X-S10 只开放 SD 内录 H.264 8-bit 的现象并不矛盾。** 实际菜单/业务逻辑可能仍不展示或从不请求数值 1；其它合法性约束可能存在于 UI 菜单选择阶段、VPU/录制任务、流文件封装或传感器可用组合检查中。对应第四个 32bit 编码参数 \`input[3]\` 的数值 1/3 差异**尚不能**被视为 bit-depth/profile 枚举。

## 5. 一项相关但不能误判的上层差异

Ghidra 交叉引用显示：

- X-T4 \`FUN_0112FD80\` 有 **4** 个明确的直接调用点，其中 \`FUN_0115B234\`（640 字节）负责在某种模式/设置切换流程中依次恢复数个用户设置，最后读取 \`0x3E4 / 0x3E5\` 并刷新电影格式 / H.265 codec 配置。
- X-S10 \`FUN_0115B578\` 有 **3** 个直接调用点，观察到菜单/初始化两类调用；**没有发现上面这个 X-T4 模式切换函数的额外直接调用**。

这表示两机状态恢复流程可能有所不同，但 X-T4 的额外调用完全可能源自实体操控布局、切换模式设计、个性化设置等**非 Main10 功能**。不能直接把差异当成“允许 10-bit 的唯一开关”，也没有任何根据认为直接移植该函数是安全的。

## 6. 下一阶段尚缺的证据（更加具体了）

1. 找到 **H.265(1) 真正写入录像 context / VPU 编码 Session 的生效路径**，确定是“仅通用设置合法”还是实际能从用户当前可选 UI 进入编码初始化。
2. 通过两个官方可内录 Main10 的正对照还原并定义视频码流 **HEVC Main10 profile、内部 4:2:0 10-bit 输入格式**的字段与参数来源，区分码率与预设值。
3. 在 X-S10 上确认是否存在最后一层 profile/像素格式/机型策略检查；如有明确差异，才考虑修复；没有实证就**不能做固件补丁**。
4. 4K60 仍需证明上层 UI/传感器 ISP 许可；第十五阶段已证明**4K59.94 的底层 LUT 六条候选记录全部存在且与 X-T4 相同**。
5. 无论上层软件是否允许，最终实机固件刷写还必须独立解决压缩封装/校验/签名、同机固件版本地址、诊断风险和救砖方案。
