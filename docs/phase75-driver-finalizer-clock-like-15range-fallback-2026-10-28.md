# Phase 75 — `0xFFF7B828`命令参数的数值档位/无条件兜底：并非“没中某个时钟窗就拒绝”（2026-10-28）

## 主要结论

在 Fuji **X-S10 v3.11 / X-T4 v2.12** 原始X6 Section1与只读Ghidra中，Phase73–74追踪到的**同一个`0xFFF7B000`驱动命令上下文**有一个后续数值档位计算器：X-S10 `FUN_0126E804`、X-T4 `FUN_01244A1C`。该函数按照其他上下文字段计算出一个32位无符号数值，在独立的**15行×5个uint32**ROM表中选档，将相关配置编码进**偏移`+0x828`**（给定常量基址，有效CPU写入地址`0xFFF7B828`）。

**新关键事实：前14行是窄范围，第15行是`[0,0xFFFFFFFF]`的兜底**；两机原始300字节表**逐字相同**，SHA-256为`7670399720422b89e5d7dde5f44382ad87da3b018841b9723e246841d4deb236`。因此只要计算出了合法的32位无符号数值、ROM表未改，这个原厂**范围匹配循环不会仅因数值落在前14个窄窗口之外而返回失败**；最后一行总会匹配。原始代码虽然保留了`if (iVar1 == 0xF) return 0xFFFFFFFF`，但对这个静态原厂表而言，纯范围搜索不需要走到`iVar1=15`。**这不等于整个函数恒返回成功**：另有`switch`类码默认失败分支，且计算时的输入/算术状态仍未知。

## 1. 双机真实ARM、指针、数值公式与类别码

| 原厂锚点 | X-S10 v3.11 | X-T4 v2.12 |
|---|---|---|
| 命令构造器 | `FUN_0126D1FC` | `FUN_01243414` |
| 数值档位函数 | **`FUN_0126E804`** | **`FUN_01244A1C`** |
| 原始ARM构造器→档位函数BL | `0x0126D298` | `0x012434B0` |
| 原厂ROM的表指针常量地址/值 | `0x0126E9EC`→`0x0162E4C4` | `0x01244C04`→`0x016063E8` |
| **15×20字节表首址**（首行范围下限） | `0x0162E4C0` | `0x016063E4` |
| 初始比例字段首址，首3组32位数值对 | `0x0162E4A8`；`1/1, 5/4, 3/2` | `0x016063CC`；同构 |
| 后续读`+0x828`的原始A32 | `0x0126E900` | `0x01244B18` |
| 随后的写`+0x828`的原始A32 | `0x0126E908` | `0x01244B20` |

原厂Ghidra可见它从调用者上下文**`+0x8`、`+0x0C`、`+0x50`**获取参与比例运算的字段，并由**`+0x4B0`**提取类别码。代码依据前者部分位标志选择分子/分母，对另一字段进行乘除，得到范围查找的`uVar3`；不要根据数值形状推断所有上下文字节都来自GUI或Recorder。阶段73中已证实接口记录索引只流进命令字`+0x624`的两个位，本阶段**没有证明这些额外算术输入也来自同一接口记录或Movie四参数**。

所有支持的类别码是**`0、2、3、8、10、12、14`**。它们决定查表第三、四或第五个字并选择左移0/1/2位；**其它类别码会通过`switch default`返回`0xFFFFFFFF`**。根据原厂只读表校验，上述七个支持类别在15行中的派生数值均为非负、符号位未置。因此**真正可能触发的静态显式类别错误与“数值没落入窄范围”是完全不同的问题**；更早的分母有效性/设备状态另需独立证明，不应夸大为整个函数没有失败可能。

## 2. 为什么怀疑这是视频/HD接口时钟档，而不是传感器或编码器FPS锁

窄窗口围绕以下数值（直接源于双机ROM，在表中均有实际狭窄区间）：`25175、25200、27000、27027、54000、54054、74175、74250、148352、148500、296704、297000、593407、594000`；这些数值若解释为kHz，**很接近视频接口常见25.175、27、74.25、148.5、297、594 MHz级像素时钟**，还出现了分数帧率与整数帧率相近的两组频率。附近驱动日志/代码还包含`HD_`相关控制路径。这是强烈的*接口时钟分类*线索，但**尚未取得独立时钟寄存器规范、设备ID、具体接口物理映射或实机信号测量**，因此“这些数字确实是HDMI时钟kHz”仍是推断而非原厂代码已命名的物理事实。

无论如何，该表不是前面确认的**Movie 96行分辨率×帧率/码率矩阵**，也不是传感器36条接口模式表。不能把第14行的“594000附近”与“相机能内录3840×2160 59.94p/HEVC Main10”画等号。即使这里允许594000这一数值，也只是**给某个上下文计算值选到某行参数**，并不保证信号真实输出或编码器接受。

## 3. 负证据：范围搜索不会独自阻挡任意u32，但类别/算术/硬件仍未知

Ghidra函数的循环结构是：从首行上界指针开始，若无`下界≤uVar3≤上界`就将指针加**5个uint32**，`iVar1++`；当`iVar1==15`才返回失败。由于第14索引行为`[0,UINT32_MAX]`，它是**对所有u32的完备覆盖**。本阶段用原创纯函数对以下人工取值检查：0、1、25175、27000、74250、148500、297000、594000、UINT32_MAX，均能命中某行；不在任何前14窗口的数值会匹配第14索引的最后一行。原始二进制额外通过整个300字节表的SHA固定，防止将偶然的`0,UINT32_MAX`错误归因于其它表。

Ghidra所显示的其余返回`0xFFFFFFFF`路径**仍存在**：不支持的类别码直接失败；计算中的零分母、尚未确认的源参数或实际外设状态都不在这个纯表结论的安全证明内。对类别支持的结果，函数在原厂代码中将值打进`+0x828`，**这不是设备硬件传输成功的返回值**，更不是VPU编码器成功的事件。
