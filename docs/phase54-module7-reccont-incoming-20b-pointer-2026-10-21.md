# 第54阶段：找到了模块7 `reccont` 真正的收件线程、0x20B载荷指针写入描述符及条件式源快照消费者（2026-10-21）

> **实质进展**：不再单靠第53阶段的发送端 `type=0x20B` 和 Recorder 另一侧“碰巧同样的消息类型”推断关联。对 X-S10 **3.11**、X-T4 **2.12** 两套原厂ARM/Ghidra做只读复核后，找到了真正注册到**模块7**的 `reccont` 任务回调，以及模块7队列接收函数。原始指令显示：成功取回消息后，从消息第8字节开始提取消息体，并按消息体长度复制到接收描述符 **`+0x08`字段指向的位置**；两机 `reccont` 初始化均将该字段赋值为**描述符 `+0x0C` 自身**。因此，在第53阶段的8字节`0x20B`消息成功投递、指针保持有效、没有被后续代码改写的条件下：**`desc+0x0C` 将得到GUI完整暂存缓冲区的地址，`desc+0x10`将得到发送方的序列值**。另在不同的Recorder控制器中找到对同一描述符`type==0x20B`时读取`desc+0x0C`指针并复制整份配置到**Recorder源快照**的原始ARM路径。上游到描述符的通信数据边已闭合为**条件式静态代码链**，但尚无运行态真实成功送达/执行序列的证明。
>
> **极关键的边界和纠错**：这个`0x20B`消息体中的第二个32位字**不是**当前Recorder指针P。它正好占用`desc+0x10`，而`desc+0x10`也在另外一条**`type==0x200`**初始化路径中用作P的指针字段。两种消息类型的时间状态不可混用；**不能把先前对`0x200`字段的语义硬套到正在处理的`0x20B`消息**。因此仍不能宣称`P==GUI`、`P+0x581`初值已找到，或4K60/HEVC Main10已可用。

## 2. 原始模块7收件函数：复制的是消息体到描述符指针指向的内存

| 接收处理环节 | X-S10 | X-T4 |
|---|---|---|
| 任务回调 | `FUN_021C549C` | `FUN_0212EA80` |
| 接收调用原始BL | **`0x021C54D0`→`FUN_012A62D0`** | **`0x0212EAB4`→`FUN_0127E9D0`** |
| 接收时实际第1参数 | `7` | `7` |
| 接收时实际第2参数 | `&desc` | `&desc` |
| 原厂队列服务 | `func_0x00053C4C`（映像外） | 同左 |
| 头类型和长度恢复 | `LDRH/STRH` `0x012A6304/08`及`LDR/STR` `0x012A631C/20` | `0x0127EA04/08`及`0x0127EA1C/20` |
| 条件：`len != 0` | `LDR/CMP/BNE` `0x012A6324–2C` | `0x0127EA24–2C` |
| **消息体源地址** | 从队列消息对象起点**`+0x08`**（`0x012A6374`） | 同左（`0x0127EA74`） |
| **消息体目的地址** | `LDR R0,[R5,#8]`（`0x012A6378`），R5为接收方头指针 | `0x0127EA78` |
| 复制调用 | **`0x012A637C`→`FUN_012A9148`** | **`0x0127EA7C`→`FUN_01281848`** |
| 处理完成消息释放 | `func_0x00050AAC` | 同左 |

关键的真实代码语义：

~~~c
// BOTH models, simplified condition on successful queue-receive:
receiver_desc->type = queued_msg->type;      // 16bit
receiver_desc->body_len = queued_msg->length; // 32bit at desc+4
if (queued_msg->length != 0) {
    memcpy(receiver_desc->body_ptr, queued_msg + 8, queued_msg->length);
}
// desc->body_ptr = desc+0x0C was set during reccont task initialization
~~~

同一回调在队列返回成功后还有一组**特例预检查**（X-S10 `FUN_0225E9A8`，X-T4 `FUN_021CB620`），如果返回1，直接重新等待下一条消息，不继续后面的状态机；否则有原厂BL执行`memcpy(desc+0x0C, *(desc+8), *(desc+4))`（X-S10 `0x021C5514`，X-T4 `0x0212EAF8`）以及消息标注函数，随后进入Recorder FSM。这里的第二次复制在`desc+8`仍指向`desc+0x0C`时可以是**自身复制**；不能将它误认为从GUI向Recorder P的第二次赋值。

## 3. 消息8字节在接收描述符内的真正含义

沿上一阶段原厂发送函数继续核验，`0x20B`消息有8字节消息体：

~~~text
发送方GUI对象（GUI+0x581, GUI+0x5B0属于完整结构）
  X-S10 GUI 0x01B880A0 / X-T4 GUI 0x01AF2808
       │ memcpy 0x5DC / 0x5D8 [已有Phase53硬证据]
       ▼
发送方完整暂存 XS10 0x028EBA8C / XT4 0x0284898C
       │ 消息体仅8B： [0] = 上述暂存地址，[4] = 序列值
       │ 0x20B；模块7；原厂OS queue提交函数
       ▼  （交付/执行是条件，不是实际采样）
模块7 `reccont` 收件回调
       ├─ desc.type      = 0x20B
       ├─ desc.body_len  = 8B
       └─ *desc.body_ptr = 接收8字节；初始化desc.body_ptr=desc+0x0C
                 │
                 ├─ desc+0x0C = 暂存区的四字节地址（指针，不是配置本身）
                 └─ desc+0x10 = 序列值（不是Recorder P指针）
       │ 特例过滤未截走 + 后续状态条件满足时
       ▼
另一个控制流程 `FUN_0221C934` / `FUN_02189348`
       │ 条件 desc.type == 0x20B && desc[+0x0C] != 0
       │ memcpy 0x5DC / 0x5D8 (源=*desc+0x0C)
       ▼
Recorder **源配置快照** XS10 0x02D9D284 / XT4 0x02D109D4
       │ 其它阶段已核对的后续活跃配置链：是否同一事件时执行未知
       ▼
【尚未知】GUI实际运行态值→Recorder当前P+0x581/+0x5B0初值
~~~

**重点：** 在`type==0x200`时，原有`FUN_02214738`/`FUN_02180D0C`初始化器把描述符**`+0x10`**的四字节当作主配置指针P的来源；可是这次`type==0x20B`的**相同字节位置**来源是消息体第二个word、即序列值，不能视作P的地址。因此本阶段找到了GUI到**Recorder源快照**的**条件式代码通路**，没有因此直接证明GUI到**当前P内存**的同一通路。

## 4. 特例过滤：原始ROM表内没有`0x20B`，并非单凭消息ID自动归队

| 静态边界 | X-S10 | X-T4 |
|---|---|---|
| 特例消息过滤/回调 | `FUN_02279708` 经`FUN_0225E9A8` | `FUN_021E7374` 经`FUN_021CB620` |
| 原始ROM中16B步长的特例表 | `0x02690D40` | `0x025EFAB4` |
| 按原始结构遍历到零结尾的表条数 | **279** | **278** |
| type `0x20B`条目 | **0** | **0** |
| 另一个例外 | 此处没有另证0x20B绕过 | X-T4 `FUN_021F1E28`仅特别处理`0x123A` |

按原厂ROM字节逐个解析16B记录的类型字段，表中没有精确的`0x020B`。因此本阶段的代码逻辑中，**0x20B不会因为该特例类型表命中而被截走**，保留了进入正常描述符/FSM分派的路径。这个筛选基于已识别的静态表和原厂Ghidra分支，**不意味着所有异步门控、队列失败、并发别名或上层状态一定允许该条消息完成**。

对Recorder FSM中的另一组`0x20B`条件映射也进行了有界核查；属于`type`判断的函数与模块7事件分派间依然存在路径条件。不能把上面经过接收循环的消息**必然**接到后面处理快照的成功分支。

## 5. 找到真正复制目标：是Recorder源快照，并与第26阶段交叉对上

| 条件复制证据 | X-S10 | X-T4 |
|---|---|---|
| 单独控制函数 | **`FUN_0221C934`** | **`FUN_02189348`** |
| 控制器调用该函数的ARM BL | `0x021CDF8C` | `0x02137558` |
| 比较当前描述符type是否是`0x20B` | `0x0221C95C/C960` | `0x02189370/374` |
| 从当前描述符`+0x0C`取完整配置源指针 | `0x0221C9E4` | `0x021893F8` |
| 只有源指针非零才做复制 | 条件分支已核验 | 同左 |
| 原厂复制字节数 | `0x5DC` | `0x5D8` |
| **memcpy BL** | **`0x0221CA04`**→`FUN_012A9148` | **`0x02189418`**→`FUN_01281848` |
| **目的地址ROM literal** | `0x0221CA10`→**`0x02D9D284`** | `0x02189424`→**`0x02D109D4`** |

目的地址与**第26阶段的Recorder源快照基址完全相同**，覆盖源快照内的`Codec/Format+0x5B0/+0x5B1`及模式标志`+0x581`。这是与第53阶段相互独立的ROM值与复制参数的交叉验证。受控条件：处理函数只有在`type==0x20B`且`desc+0x0C`非空时复制，控制器本身又位于有状态的FSM/录像准备路径上；**本轮尚未证明它恰好在刚才同一条GUI消息之后运行**，也没有证明它总是使用GUI暂存地址或者那个暂存指针在使用时仍有效。将此称为“可由上述消息提供数据的条件式消费者”，不能称为“实机GUI设置已导致内录生效”。

## 7. 第55阶段应查的最后关键门控

1. 原厂Recorder FSM里，`0x20B`接收消息走到`FUN_0221C934`/`FUN_02189348`所在事件/控制分支的**完整条件与时序**，特别是写入源快照之前有无其他最新消息覆盖描述符或发送暂存区。
2. type `0x200`初始化P与type `0x20B`载荷暂存地址在不同事件之间是否通过其它复制/缓存/恢复路径发生交汇，严格区分描述符`+0x10`的**两种运行时语义**。
3. 通过源快照提交到真正Recorder活跃Codec/Mode的先后关系；源配置`+0x581`是否会经历进一步规范化。之后才可能研究VPU Main10真正的位深配置和4K60传感器/ISP/写卡能力。
4. 任何机身验证都必须另行获得相应版本ROM/签名/救砖前提并评估风险，当前**完全没有**可刷安全补丁，勿操作真实相机。
