# Phase 68 — X-S10 与 X-T4 2160P/FPS6 的四参数静态联合条件及独立接口模式列表（2026-10-27）

**结论必须分成两个层次：**研究样本 X-S10 固件 3.11 和 X-T4 固件 2.12 都有满足全部四项 GUI 录像设置的**各自原厂菜单允许值**，并具有六条 2160P/FPS6 的静态联合模式表记录；但是录像设置加载器会进行额外条件重写，原厂还有通过 `0x302` 运行时通信内容填充的接口支持模式列表、候选排序、首帧类型类别和 Recorder 父对象的独立状态。**四个参数分别允许，不等于运行时可同时保持，更不等于实体 X-S10 支持 4K59.94 / HEVC Main10 内录。**

## 1. 不靠推测而是直接读取的四份 ROM 模式参数索引

两机 Section1 模式列表分别含 24 / 9 个有效模式，电影模式 `0x2D` 均在列表中。参数索引分别含 **252 / 254** 条8字节索引；每个候选数值附有 **28 / 16** 字节逐模式允许/默认标志。原厂合法性校验器接受标志 `1–4`，带 `2/4` 的候选为默认。审计核对了全部候选顺序、包含重复数值4/6的 FPS 表及这些候选的所有 `0x2D/0x21` 标志，绝不把重复数值行漏掉或当成同一记录。

| 真实原厂菜单字段 | X-S10 参数ID | X-T4 参数ID | 电影模式0x2D允许数值 | 电影模式默认 |
|---|---|---|---|---|
| `eaPixel_Movie` 像素尺寸 | `0x3F4` | `0x3DD` | `7=4K`、`6=FullHD` | **7** |
| `eAspect` 画幅 | `0x42B` | `0x413` | `2=WIDE`、`7=17:9` | **2** |
| `eMovieFps` 普通录像FPS | `0x3F6` | `0x3DF` | `1,2,3,4,5,6,8,9,12,13` | **4** |
| `eMovieBps` 码率档位 | `0x3F9` | `0x3E2` | `3=400M, 2=200M, 1=100M, 0=50M` | **1** |

参照模式 `0x21` 更严格：像素仅允许7、画幅允许1/2/3、FPS仅允许4、BPS仅允许1。**相同的GUI与参数表不是同一真实可录机身能力的证据。**

## 2. 菜单加载器对四个字段存在不独立的条件修改

逐机原厂只读Ghidra跟踪：

- 像素尺寸加载器 X-S10 `FUN_01174FE4`、X-T4 `FUN_01148FE8`：读取上述像素参数ID并按电影模式`0x2D`检查值；不合法采用原厂默认，随后调用专用 `eaPixel_Movie` setter。
- 画幅加载器 XS10 `FUN_011766E4`、XT4 `FUN_0114A5D8`：校验 mode（调用方可以传 `0x2D`）、参数ID `0x42B/0x413` 和候选值；但是 GUI 当前模式为 `'-'`（字节 `0x2D`）时，可以直接调用无参数/当前值方式的 setter，所以不能假定每次都会重新设置。其它UI缓存及状态恢复路径也可能恢复先前值。
- 普通FPS加载器 XS10 `FUN_01176904` / XT4 `FUN_0114A7F8`：内部选择器 ID `0x400/0x3E9` **等于0时**采用普通FPS ID `0x3F6/0x3DF`，经模式合法性校验、回退默认；**不等于0时**改从另一个 ID `0x402/0x3EB` 取值。另有电影状态字段等于7时直接将GUI FPS设为枚举**4**（29.97），从而排除这个具体时刻的FPS6条件。
- 码率加载器 XS10 `FUN_01176AA4` / XT4 `FUN_0114A998`：选择器为0时正常读取/校验 `0x3F9/0x3E2`；选择器**非0时强制码率枚举2（200Mbps）**，不保留用户设置的100或400Mbps。
- 独立播放 FPS `eMoviePlayFps` 加载器同样使用此选择器，普通模式回退时会用普通FPS的`0x2D`准入表验证，并另有状态为7强制4。它进入 Movie+0x5C7，**不是**类别0联合4K表使用的Movie+0x5C6。

**不能从地址中的 `0x400`、`0x3E9` 或字段名称推测它们就是 `eMode4kOut`。**前者是设置服务的选择器ID，其业务含义尚未确定；后者是真实GUI/Recorder结构 `+0x581`，经过第49/58阶段条件式输入→活动Recorder→父对象`+0xA8E`传递，它们不可混为一个开关。

## 3. 交叉到真正的96×64联合模式表

第46–47、64–67阶段已逐指令核验：

1. GUI四参数先在允许的状态下沿 `GUI→Recorder P→转换器→活动配置模板→Movie` 结构复制；依次成为Movie `+0x5BD`(像素键低8位)、`+0x5BE`(画幅键高8位)、`+0x5C6`(普通FPS)、XS10 `+0x9B8` / XT4 `+0x9BC`(码率档)。这是跨线程、可能失败的条件式消息路径，**不是一个原子操作**。
2. 首个Movie上下文构造时，类型1/4/5/6/7通常属于类别0，类型2或3分别属于类别1、2。类别1/2查表使用独立播放FPS +0x5C7，而六条2160P/FPS6记录均**要求类别0**。
3. 如果Movie类型是4–7且父Recorder真实 `+0xA8E == 1`，查表像素键低8位会由7**改为6**。这与当前菜单像素7是否被接受，是两种不同的条件。对Type1，该条件分类器不会重写；但**并未证明Type1在相关机型提供预期4K录制功能**。
4. 类别0 / 像素低键7 / WIDE画幅2 / FPS6 / BPS1、2、3：原厂表行33、34、35→3840×2160；17:9画幅7对应行15、16、17→4096×2160。码率0=50M没有此组合。强制低键6之后，100/200M会匹配各自1920×1080或2048×1080静态行；**400M的同类低键6组合无匹配记录**。不得据此假定机身会启动或故障——真实上游状态可能根本不允许反事实条件出现。

**纯静态条件式充要性仅限此特定ROM四键查表函数**；这不是完整摄影系统（UI、队列、录像状态机、sensor、ISP、VPU、SD写卡）的充要条件。

## 4. 另一份运行时接口模式门控，仍无动态内容

两机 Section1 另有**36条×16字节一致的接口模式描述记录**，偏移 `+0x0` 为模式ID、`+0x0A` 为一组取值24/25/30/50/60的数字，不能脱离上下文直接认定是实机传感器实际输出帧率。索引22/23的ID=97、34/35的ID=102，`+0x0A=60`；**这些索引不等于录像模式ROM的行号**。

接口支持ID的判断器 XS10 `FUN_01269634`、XT4 `FUN_0123F84C` 从**运行态ID名单及位图**读取结果。该名单通过含`0x302`标记的数据包分支动态填充，列表中可见长度上限`0xC0`及字节处理；**本研究没有接收到实际设备响应或读取相机内存**。另外，默认候选优先级也被独立的列表设置器复制到 RAM，运行时还可按配置指针更新；后续选择器在迭代索引时会调用支持性检查，并可能走其它候选或特殊状态分支。所以无法知道X-S10实机当前是否包含ID97/102，更没有看到哪个具体接口ID最终对应四键2160P录制选择。
