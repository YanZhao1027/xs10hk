# Phase 74 — 接口记录与运行时状态同时进入同一驱动命令字（2026-10-28）

**研究样本**：Fujifilm X-S10 固件 3.11 与 X-T4 固件 2.12；历史实体 X-S10 是 2.10，未参与任何操作。原厂Section1二进制与Ghidra数据库只读，保存在本机Git忽略的`output/`。**研究结果是静态 ARM 与条件式控制流，不是实际4K60/HEVC Main10、ISP、VPU或相机硬件成功验证。**

## 1. Phase73 的接口记录索引派生值确实被第二条状态更新路径保留

Phase73已证明：0x302接口应答→反向选择的接口记录索引→描述符`+0x08`→本地字节值0或2→调用打包器，将`(local_68 & 3) << 20` 写进**命令上下文`+0x624`位20–21**。其中原厂ID97索引22/23生成`0x00200000`，ID102索引34/35生成`0x00000000`。本阶段沿打包器**后续原厂调用**进一步确认：同一初始化函数立刻运行另一个状态编码器，且下游以**读-改-写**方式操作**同一个`+0x624`字**，但仅改位22–23和位28–30，完全不改位20–21。

| 原厂证据（全由原始A32 BL / Ghidra核验） | X-S10 v3.11 | X-T4 v2.12 |
|---|---|---|
| 驱动启动函数 | `FUN_0126C388` | `FUN_012425A0` |
| 首先调用Phase73命令构造器（`0xFFF7B000`、传入接口记录派生字节） | **`0x0126C944` → `FUN_0126D1FC`** | **`0x01242B5C` → `FUN_01243414`** |
| **紧邻的下一条BL**再编码运行时状态（当前状态字段等） | **`0x0126C948` → `FUN_0126AE08`** | **`0x01242B60` → `FUN_01241020`** |
| 状态编码器又调用同字读-改-写器 | `0x0126AE58` → **`FUN_0126D6B4`** | `0x01241070` → **`FUN_012438CC`** |
| 两条路径同时传入的固定上下文基址 | `0xFFF7B000` | `0xFFF7B000` |
| 打包器原始`str`写`+0x624`的机器码地址 | `0x0126F184` | `0x0124539C` |
| 状态更新器原始`ldr`读`+0x624`的机器码地址 | `0x0126D6C4` | `0x012438DC` |
| 状态更新器原始`str`再次写`+0x624`的机器码地址 | `0x0126D708` | `0x01243920` |
| 以调用参数计算的**有效存储地址** | **`0xFFF7B624`** | **`0xFFF7B624`** |

`0xFFF7B624`是原厂ARM指令以常量参数和固定偏移计算的**CPU有效地址**。其是否属实际MMIO寄存器、FPGA/驱动映射窗口、硬件状态含义及写入完成情况**没有独立验证**。因此不要把“发现存储指令”直接说成“硬件已启动/接受某模式”。

## 2. 后续状态编码器的精确条件、掩码和哨兵处理

X-S10运行态输入：`_DAT_01C85688`、`DAT_01C84F8A`、`DAT_01C84F8C`。X-T4对应 `_DAT_01BE5754`、`DAT_01BE5056`、`DAT_01BE5058`。`DAT_...4F8A/5056`出现在Phase70解析响应缓冲区指针与Phase73所追踪的后续驱动读者中；其**实时值并未取得**，其他原厂写者仍可能覆写。

原厂状态编码器先决定两个小整数`p2,p3`，再用读-改-写器处理`+0x624`与`+0x614`：

| 原厂条件（**不等于电影FPS6枚举条件**） | `p2`（字位22–23） | `p3`（字位28–30） |
|---|---:|---:|
| `(statusword & 0xFFFF00)==0x10100`，类型值为1或2 | 3 | 5 |
| 同上，类型值不是1/2 | 3 | 6 |
| 非上述状态；类型值0或1；另一个标志为0 | 1 | `0xF`（保持原值） |
| 非上述状态；类型值0或1；另一个标志非0 | 2 | `0xF`（保持原值） |
| 非上述状态；类型值2及以上 | `0xF`（保持原值） | `0xF`（保持原值） |

- 当`p2 != 0xF`时，原厂执行`(word624 & 0xFF3FFFFF) | ((p2 & 3)<<22)`，同时清除另一个控制字`+0x614`的`0x00080000`；当`p2==0xF`时反而置该标志且**不覆盖**`+0x624`的22–23位。
- 当`p3 != 0xF`时，原厂执行`(word624 & 0x8FFFFFFF) | ((p3 & 7)<<28)`，同时清除`+0x614`的`0x00200000`；当`p3==0xF`时置该标志且不覆盖28–30位。
- 两条掩码均不触及**Phase73接口记录所决定的第20–21位**。即使进入“特殊状态”，旧的ID97/ID102派生结果也**不会被此函数清零/翻转**。这只证明当前这两个调用步骤的按位关系，后续并发写者或不同初始化周期仍可能改写整个字。
- 同一函数还对上下文`+0x81C`执行`&0x00FFFFFF`；并不代表清除了`+0x624`。原厂将`p2/p3==0xF`作为“该子字段保持、标志置位”的内部哨兵，不应把`0xF`当有效码值写入相应子字段。

对人工合成“ID97配置位`0x00200000`”与“ID102配置位`0`”应用同一状态更新：两者最后依然在位20–21相差**`0x00200000`**。所有数值只是固件按位模拟；**不是**实体X-S10模式、时序或信号测量。

## 3. 第三条入口：运行态状态5时可能再次更新同一命令字

两机另有一条**独立的调用路线**：X-S10 `FUN_0126C0FC`、X-T4 `FUN_01242314`。它们先用输入字节更新上述状态字的高部分，**仅当共享状态仍等于5时**，才再次调用相同编码器`FUN_0126AE08`/`FUN_01241020`，然后调用带`0xFFF7B000`常量基址和`0x4000`/`0x2000000`值的额外接口控制函数。

原厂直接BL分别为 `0x0126C11C`→`FUN_0126AE08`、`0x01242334`→`FUN_01241020`；这两个状态5门控函数又分别经`FUN_01269494`/`FUN_0123F6AC`被包装调用（BL `0x0126949C`/`0x0123F6B4`）。它们的**运行态触发条件/上游队列传递和实际执行次数未知**。不能断言一定发生，不能由此推断录制中动态切换1080/2160或60fps。

## 4. `+0x828`也有真实写入地址，但尚无硬件成功证明

Phase73的命令构造器最后调用15段数值查找与分类函数 X-S10 `FUN_0126E804` / XT4 `FUN_01244A1C`，按`+8/+0x0C/+0x50/+0x4B0`的其他上下文字段导出结果，在匹配条件下对**同一调用基址的`+0x828`**进行读-改-写。原始A32指令对：X-S10 **`0x0126E900`读、`0x0126E908`写**，X-T4 **`0x01244B18`读、`0x01244B20`写**。当`param_1=0xFFF7B000`，其有效地址是**`0xFFF7B828`**。这并不证明该地址是实体MMIO，也不意味着函数返回0即传感器已接受2160P60；函数有查找失败返回`0xFFFFFFFF`的路径，上一层没有将其等同于实机已编码的视频帧。

对两机Ghidra全Section1/2执行了固定偏移`0x624`/`0x828`及邻近字段的指令扫描：发现不少**其他、不一定别名的结构体**也使用相同偏移。因此**仅凭同样的偏移不能确认另一个Movie/Recorder数据结构与驱动共享基址**。本阶段以明确的同一`0xFFF7B000`调用参数、两层函数传参、原始BL和两次读写机器码为正证据；没有通过不可靠的“偏移字符串相同”声称找到了Movie直接消费者。
