# 第十三阶段：加入 X-T3 5.11 作为 4K60 / 10-bit 正对照（2026-10-14）

> **本轮最重要的结果：X-T3、X-T4、X-S10 三份原厂固件中的三个视频 codec 模块共 741,376 字节逐字节完全一致，0 字节差异。Ghidra 还确认三机均有相同结构的 H.265 参数接收→VPU 参数装载→事件分派→Session 映射路径。**
>
> X-T3 / X-T4 是已支持 H.265 10-bit 与 4K60 内录的“正对照”；这些证据强烈削弱“X-S10 缺少 HEVC 编码模块”的说法，但**并未证明它的录像任务能提交 Main10 参数，也未证明 4K60 的传感器与写卡路径可用**。
>
> 本研究**只处理用户授权 Ubuntu 上的原厂固件副本**，未操作相机 USB/FF80，未修改或生成可刷写固件。所有厂商二进制及 Ghidra 数据库留在 Git 忽略的 `output/` 中，未提交 GitHub。

## 2. 决定性的三方逐字节对比：741,376 字节三机完全一致

下表偏移均为**恢复后的 Fuji payload 文件偏移**，不是运行时 RAM 位置：

| 厂商模块 | 大小 | X-T3 5.11 的区间 | X-T4 2.12 的区间 | X-S10 3.11 的区间 | 三机不同字节 |
| --- | ---: | --- | --- | --- | ---: |
| H.265 / HEVC encoder | **425,984** | `0x02C60000:0x02CC8000` | `0x02C40000:0x02CA8000` | `0x02DA0000:0x02E08000` | **0** |
| H.264 encoder | **233,472** | `0x02CC8000:0x02D01000` | `0x02CA8000:0x02CE1000` | `0x02E08000:0x02E41000` | **0** |
| H.264 decoder | **81,920** | `0x02D01000:0x02D15000` | `0x02CE1000:0x02CF5000` | `0x02E41000:0x02E55000` | **0** |
| **总计** | **741,376** | | | | **0** |

各模块的 SHA-256：

- H.265 encoder：`9d986c77d71a57ceefbd6b0bde2668f1a057f6892daff3be0fb4a4a3c5f4441c`
- H.264 encoder：`3baf997561ea106e831bd9107acb7476997492a36df886dedfe275fb31c74243`
- H.264 decoder：`58ec013d91c20f673f55131fc43840d8a65d8c72fb63dff76f9846547bac9508`

本轮**重新从 X-T3 5.11 原厂 DAT 提取**三个视频模块，与此前从另外两机提取的模块逐字节比对。三组两两组合（X-T3/X-T4、X-T3/X-S10、X-T4/X-S10）均为 **0 字节差异**。

原始 HEVC 模块的标识字符串为 `H.265 MP Encoder`。这里的 `MP` **没有得到能可靠证明它代表 Main10 的解释**；不能仅凭这个标识推断 profile。基于两个官方 Main10 正对照模型实际使用同样的完整模块，**“X-S10 缺少编码器固件模块本体”已经是较弱的假说**。但模块是否装载、RAM/硬件是否有能力执行 Main10、Main10 的设置是否成功，都还需要单独证明。

新增可复现工具 `tools/three_way_codec_audit.py`：只读三个本地 payload，验证正确的 codec 描述符、完整字节比对和 SHA-256，不改变固件。测试仅包含人造数据，未上传任何原厂二进制。

## 3. 原厂本地化资源有区别：10-bit 内录相关条目并非三机都有

对三份**按位取反还原的原厂 DAT payload**做 UTF-16LE 精确子串计数：

| 字符串 | X-T3 5.11 | X-T4 2.12 | X-S10 3.11 |
| --- | ---: | ---: | ---: |
| `4:2:0 10bit` | **52** | **23** | **0** |
| `H.265` | **175** | **105** | **0** |
| `4:2:2 10bit` | **70** | **69** | **46** |

这和“两个正对照机身内录 4:2:0 10-bit；X-S10 支持 HDMI 4:2:2 10-bit 而仅提供 8-bit 内录”的现有机型说明**相符**，说明某一层菜单、说明文本或本地化资源确实有差别。

**边界：** 字符串的缺失≠真实禁用分支的代码位置。不能把这些文字直接当成 patch 地址，固件 UI 资源可能采用多层查表/动态列表。各机字符串出现次数还受到地区语言/构建版本影响，计数差不等于功能数目差。

## 4. 更强的 ARM 证据：三机存在四级 H.265 驱动调用结构

Ghidra 自动分析后，用仓库中的 `ghidra_scripts/ProbeX6Refs.java` / `TraceX6Function.java` 查询以下可执行函数，全部确认存在直接 BL 调用或相应读写状态：

| 函数职责（根据反编译行为命名） | X-T3 5.11 | X-T4 2.12 | X-S10 3.11 | Ghidra 函数大小 |
| --- | --- | --- | --- | ---: |
| H.265 编码参数接收与暂存 | `0x01099274` | `0x011CD230` | `0x011F9B84` | **368 B** |
| 接收事件后的 VPU 参数区装载 | `0x01098004` | `0x011CBFC0` | `0x011F8914` | **220 B** |
| VPU 编码 Session 映射/等待 | `0x0109BF08` | `0x011CFECC` | `0x011FC820` | **312 B** |
| VPU 主循环中的事件分派 | `0x01098ACC` | `0x011CCA88` | `0x011F93DC` | **504 B** |

这些函数的 ARM 反编译结果显示：

1. **编码参数接收（368 B）**：检查驱动模式与序列状态；非空回调验证；将 **15 个 32 位参数（60 字节）**复制到全局缓冲，登记回调并将状态设为 2，触发调度事件。
2. **事件分派（504 B）**：判断状态值；状态 **2** 时调用 `V61_drv_set_enc_param` 参数装载函数，状态 **3** 进入 decoder 参数路径，4/5/6/7 对应其他事件；三机行为结构基本相同。
3. **参数装载（220 B）**：把刚才保存的参数结构的**前五个** 32 位值重新映射到 VPU 会话结构，并进入后续参数设置流程。
4. **Session 映射（312 B）**：三机使用相同的会话状态位、`0x33`/`0x23` 控制值、24,000 次等待上限和写入命令 `0x4f0` 等处理形状。

三机在参数装载流程中都表现出同样的字段顺序（从输入的 15×uint32 结构 `src` 到 VPU 目标结构 `dst`）：

~~~text
dst[2] = src[3]
dst[3] = src[4]
dst[4] = src[2]
dst[5] = src[0]
dst[6] = src[1]
~~~

**这为继续追踪编码设置提供了确切的函数、结构和控制流**，但这些字段的名称/单位/profile/bitdepth 还**没有**被证实。不能把 `src[3]` 等值擅自标注为 Main10 模式，更不能据此盲改 VPU 寄存器。

**目前缺口是更上游的真实录像任务如何创建这 15 个值、调用哪个 codec 配置入口，以及相关运行时参数与硬件的约束。** 三机主程序中的驱动实现相似不代表 X-S10 的高层业务代码有调用它的有效路径。观察到的外围 H.265 API 包装函数缺少 Ghidra 静态反向调用，可能依靠间接函数表或运行时 RPC，不能把 `xrefs=0` 当成未使用证据。

## 5. X-T3 推翻了“X-S10 录像上下文小所以不支持 10-bit”的过早猜测

又在 Ghidra 找到 X-T3 Segment 2 中的**真实录像上下文初始化函数**，对齐到上一阶段已经恢复的 X-S10 和 X-T4 录像函数：

| 机型 | 录像上下文初始化 | 逻辑上相当的上下文索引步长 | 十进制 |
| --- | --- | --- | ---: |
| **X-T3（已知可用 10-bit/4K60）** | `FUN_01EF8C94` | **`0x3C0E8`** | 245,992 |
| X-T4（已知可用 10-bit/4K60） | `FUN_022403C8` | `0x4B0A0` | 307,360 |
| **X-S10（未开放这两项内录能力）** | `FUN_022D3E00` | **`0x3C318`** | 246,552 |

X-T3 5.11 的上下文步长比 X-S10 3.11 **还小 560 字节**，却具有官方的 4K60 和 H.265 10-bit 内录能力。因此，上一阶段观察的 **X-T4 上下文更大**，**不能被用来论证 X-S10 缺少这些能力**。这就是三机正对照的关键价值。

注意：这些是**结构体/上下文寻址步长**，绝不是物理 DRAM 总容量，也不是编码器输入帧缓冲的大小。它们不能排除 X-S10 的其它缓存、带宽、温度或传感器限制。两机录像初始化函数使用了不同的状态字段，因此还需要进一步恢复确切结构含义，不可直接互相移植代码。

X-T3 还证实了真实录像任务存在 `recmvUpdateRecmrMode` 更新函数 `FUN_01EF6F88`、录像压缩回调函数 `FUN_01EF8154`、时间码帧率函数 `FUN_01EF7538`，这些均由真实反汇编/交叉引用确认。

## 6. 与第十二阶段一致及被修正的判断

**得到更强支持：**

- 三机都有对应的可执行 H.265 设备驱动函数，经过跨版本交叉分析；
- 三机 VPU 编码器映像精确相同，这与有两个 10-bit 正对照相互印证；
- X-S10 本地化资源不含内部 `4:2:0 10bit` 和 `H.265` 相关文字，与产品内录菜单缺失一致；
- X-S10 上层录像/菜单仍可能存在可修改的软件约束，有明确的调查价值。

**被 X-T3 正对照否定的过早猜测：**

- “X-T4 录像上下文步长大于 X-S10，因此 X-S10 不具备 4K60/10-bit 的硬件资源”。X-T3 反例清楚，这种推断**不能成立**。
- “H.265 编码器本体是 X-S10 缺少的功能”。三份原厂映像的相同模块削弱此假说，但仍需校验 X-S10 运行时装载/使用情况。

**仍没有得到的证据：**

- 三机 Main10 参数的字段编号、数值与上层生成代码；
- X-S10 将机内录像真正接到 HEVC 编码器的可达路径与有效初始化条件；
- 4K60 的传感器读出与实际帧缓冲能力；
- X-S10 的自制 DAT 重新封装校验/签名与可靠救砖流程。

尤其不能把录像模式注册表中的 `4K_59_94P` 文本或视频 codec 模块完全相同，直接当成“现在只改一个字节就能刷机”。

Ubuntu 上重现：

~~~bash
cd /home/zyubuntu/xs10hk

# 原厂 X-T3 5.11 的 DAT 之前已只读提取；以下为首次提取例子。
~~~

本次**80 项离线测试通过**。本地输出留在 `output/`。没有实机诊断命令、固件写入、EEPROM 保存或 USB 交互。

## 8. 下一阶段最需要实证的单一问题

现在最佳突破口不是编码器模块本体，也不是简单修改菜单标签，而是**可用 10-bit 的 X-T3/X-T4 如何在其上层录像初始化中创建 60 字节 H.265 编码参数**：

1. 靠 Ghidra 的间接调用链/RPC 注册找到 `set_enc_param` 的真正业务调用者，识别 15 个 DWORD 字段含义；
2. 两个正对照确认是否有共同的 Main10/4:2:0 位深设置和 4K59.94 允许条件，再检查 X-S10 对应路径；
3. 用实际符合约束的离线参数数据证明具体软件分支差异，而不是把资源文字猜成开关；
4. 最后单独解决封装/校验、签名、独立救砖和固件运行版本不一致等刷写安全问题。

**此时尚不能称为“10-bit/4K60 解锁已完成”，但可以较确定地把研究重心从 HEVC 编码器本体转到业务参数和模式策略。**
